# Kata taxonomy: editing and migration

This guide is for editors who add fields, foundations and specializations to the kata taxonomy (#82). The contract itself, with every field, its default and what validation rejects, is in [kata-metadata.md](kata-metadata.md). This guide does not repeat that reference. It covers how to use the contract, how a record moves from idea to published kata, and how the taxonomy sits on top of the routes, lessons, resources and saved progress that already exist.

It changes no program rule. The decision record for the kata and belt program is tracked in #80, and nothing here replaces it.

## Identifiers: how they are formed and kept stable

Identifiers are promises. Saved progress, outside links, other katas and search all point at them, so the build refuses to let a published one vanish. Every identifier below is collected from the live data (`liveIdentifiers` in `src/lib/taxonomy-sources.ts`) and compared with the lock.

| Kind | Form | Comes from | May it change? |
| --- | --- | --- | --- |
| `kata-id` | `PREFIX-001`, Randori `PREFIX-R01` (`kataId` in `src/lib/kata-schema.ts`) | `kataCatalog`, recipe `metadata.id`, staged foundation records, FND-001 | **Never.** A kata that changes keeps its ID. One that ends is retired, and its ID is never reused. |
| `kata-route` | `/katas/<lower-case-slug>` | hand-written pages in `src/pages/katas/`, recipe file names in `src/content/kata-recipes/` | Yes, with a move. The old route becomes a redirect. A route can never be retired without a destination. |
| `field` | lower-case slug | `src/lib/fields.ts` | Yes, with a move or a retirement |
| `outcome`, `artifact`, `capability`, `constraint`, `stack-recipe` | lower-case slug (`dimensionId`) | `kataDimensions`, plus the vocabulary reserved by the staged foundation family and FND-001 | Yes, with a move or a retirement |

Pathways (track slugs) and resources (`publisher/resource`) have their own rules: tracks never move ([track-urls.md](track-urls.md)), and resources follow [catalog-lifecycle.md](catalog-lifecycle.md). Fixture-only vocabulary (`src/data/kata-fixtures.ts`) is not locked, because no real kata may use it.

How the check works:

1. `src/data/taxonomy-lock.json` lists every identifier ever published, sorted by kind. `npm run taxonomy:lock` adds today's identifiers. It never removes one, so the lock only grows (`extendLock`).
2. `src/data/taxonomy-moves.json` is the ledger. A **move** is `{ kind, from, to, issue, date, reason }`. A **retirement** is `{ kind, id, issue, date, reason }`.
3. `checkIdentifiers` fails, saying what to do, when a locked identifier is neither in use nor moved nor retired, when a live identifier is not in the lock, when a move leads to something that does not exist, when a moved or retired identifier is used again, when moves form a cycle, and when an entry changes nothing.
4. Every `kata-route` move becomes a static redirect page: `astro.config.mjs` reads `routeRedirects` from the ledger. A chain of moves (a to b, then b to c) is flattened, so every old route goes straight to the page in use now.

## Field dictionary

For each field: what it is for, an example from the sector fixtures, and what an empty value means. "Required" is enforced by the schema. "Not recorded" is the meaning of every empty list. "Inapplicable" is explained below the table.

| Field | Required? | Meaning | Example (fixture) |
| --- | --- | --- | --- |
| `id` | yes | Stable kata ID, `PREFIX-001`; a Randori variant is `PREFIX-R01`. Never reused or renamed. | `FIXBE-001` |
| `title` | yes | What the learner does, in plain words. | "Take off wall quantities from an IFC model" |
| `layer` | yes | `foundation` (serves every field) or `specialization` (one field's version of a practice). | `specialization` |
| `outcomeIds` | yes, 1+ | The finished result the learner can show. One outcome may belong to several fields. | `traceable-batch-record` (biotechnology and manufacturing) |
| `artifactTypes` | yes, 1+ | What the learner hands over. | `quantity-schedule` |
| `capabilityIds` | yes, 1+ | The task skills practised. | `inspect-model`, `calculate` |
| `professionalReviewRequired` | yes, no default | `true` marks a professional review boundary before real-world use. It does not mean a review happened. | `true` for the IFC takeoff |
| `domainIds` | specialization: 1+ | Fields from `src/lib/fields.ts`. | `architecture-bim`, `construction` |
| `foundationKataIds` | specialization: 1+ | Foundations practised first. Must be `layer: foundation`, no cycles. | `FIXFND-001`, `FIXFND-003` |
| `stackRecipeIds` | no | Tool and agent setups that reproduce the kata. Several per field are expected. | `ifcopenshell-python`, `speckle-candidate` |
| `pathwayIds` | no | Tracks the kata belongs to. | `lab-automation-in-code` |
| `constraintIds` | no | Shared limits on the practice. | `simulation-only`, `fictional-data` |
| `externalResources` | no | Resources from the catalogue. A listed resource is not proof that an integration works. | `buildingsmart/ifc-wall-example` |
| `standards` | no | `{ name, version, applicability, reviewScope, sourceResourceId? }`. A reference, never a compliance claim. | IFC 4.3 (ISO 16739-1:2024), for reading wall quantities only |
| `verificationEvidence` | no | `{ description, method, standards? }`: what is produced and how it is checked. | "Each quantity traced to the entity and property", `self-check` |
| `beltCriteria` | no | `{ stage, criterion }` on the proposed stages `practice`, `adapt`, `demonstrate`. Awards nothing. | `demonstrate`: "Fixes one finding and shows the before and after" |
| `crossFieldTransfers` | no | Other fields where the same practice applies. | `manufacturing` |

### Not recorded versus inapplicable

The contract stores lists, and an empty list always means **not recorded**. It never means "checked and not needed". The schema has no "not applicable" value, on purpose: a missing standard or review boundary must stay visibly unanswered rather than look settled.

Only two cases are inapplicable by structure, and the schema enforces both:

- A foundation has no `domainIds` and needs no `foundationKataIds`, because it serves every field.
- A specialization never lists one of its own fields in `crossFieldTransfers`.

If an editor decides that something else does not apply, for example that no standard is relevant to a purely fictional exercise, they write the decision and the reason in the kata's tracking issue or MR. The list stays empty. `professionalReviewRequired` is the exception: it has no default, so every kata states it, and `false` waives no legal or professional duty.

## Status, maintainers and dates

The metadata contract validates structure only. For a kata in `kataCatalog`, the editorial status, maintainer and verification dates are kept where [catalog-lifecycle.md](catalog-lifecycle.md) already keeps them for every catalog item: in the kata's tracking issue and MR.

A kata that has a recipe record (#86) carries them in the record instead: `status`, `maintainer` and `review` (last verified, what was checked, next review), shown on the page. The recipe schema stops a record from claiming a check nobody performed: a passed or failed check needs evidence and a date, a fixture or draft cannot pretend to be reviewed, and a published recipe must have a real review, showcase and named maintainer. See [kata-recipes.md](kata-recipes.md#rules-the-build-enforces). The tracking issue still holds the discussion and the decision trail. "Review due" is not a stored status: the page shows it once `nextReview` has passed.

| Status | Meaning | Where it shows | Move on when |
| --- | --- | --- | --- |
| **Fixture** | A synthetic record that tests the taxonomy. It has a `FIX*` ID and a `/katas/fixture-*` route. A few have a labelled, `noindex` recipe page that shows the template; none has a hand-written page. | `tests/fixtures/`, and `src/content/kata-recipes/fixture-*.yaml` | never published; a real kata is written from scratch, with its own ID |
| **Draft** | A real record whose page, evidence or review is incomplete. It may be in `kataCatalog` only if its page exists. | tracking issue labelled draft | the publication checks below pass and a maintainer is assigned |
| **Published** | The page is live, linked from `kataCatalog` and listed in `KATA_DIRECTORY`. | the site | its review cadence passes, or a source, stack or standard changes |
| **Review due** | The last check is older than the cadence, or a change was reported. The page stays, with its last real check date. | issue, plus a notice on the page if learners are affected | the check is repeated (back to Published) or the kata is withdrawn |
| **Withdrawn** | The kata is unsafe or no longer works. Its instructions are removed or disabled, and its route keeps an honest notice or points to an alternative. | the page notice and the issue | a fixed version is reviewed (back to Published) |

Allowed moves: Fixture is a dead end. Draft goes to Published. Published goes to Review due. Review due goes back to Published, or to Withdrawn. Withdrawn goes back to Published. Never delete an ID or a route on withdrawal: saved progress and outside links point at them.

For every Draft, Published or Review due kata, the tracking issue records:

- **Maintainer role**, and the person who actually took the work, once someone has. An unassigned review stays unassigned.
- **Last verified**: the date of a check that was actually done, what was checked (steps, environment, versions) and what was not. Never backdated, and never moved by a partial review.
- **Next review**: the cadence from [catalog-lifecycle.md](catalog-lifecycle.md#what-to-review). The default is quarterly. Anything that cites a standard is also reviewed when that standard is revised.
- **Professional reviewer and decision**, only when such a review took place.

## Checklist: add a field

1. Add `{ id, name, examples }` to `src/lib/fields.ts`, using a lower-case slug. Add `trackHref` only when a track exists.
2. Write no code. The validator reads fields from that list, and the fixture test shows a new field (`maritime`) validating with no code change.
3. Connect existing content: put the new field ID in the `domainIds` or `crossFieldTransfers` of katas that already fit, and in the `track` of any lessons that belong to it.
4. Add at least one specialization (next checklist) before the field is promoted on the home page or the field page.
5. Run `npm run taxonomy:lock` and commit `src/data/taxonomy-lock.json`. From now on the field ID is a promise.
6. Run `npx vitest run` and `npm run check`. Unknown IDs fail with a message naming the kata.

## Checklist: add a specialization

A specialization is one field's version of a shared practice. It extends a foundation and does not copy it.

1. **Outcome first.** Name the finished artifact and who uses it. Reuse an outcome ID if another field already has the same result. That is the point of shared outcomes.
2. **Pick foundations.** Reference at least one existing `layer: foundation` kata. If no foundation fits, propose one separately; do not bury foundation content in the specialization.
3. **Add vocabulary.** Put any new outcome, artifact, capability, constraint or recipe ID in `kataDimensions` first. Use existing IDs where they fit.
4. **Record recipes honestly.** List at least one recipe a learner can run today. Describe any integration that has not been run for the Dojo as a candidate in the MR and on the page.
5. **Standards.** Give the edition, the applicability and what a reviewer checks. Set `professionalReviewRequired: true` for regulated, safety-critical or licensed work. Never write "compliant".
6. **Evidence and belts.** Describe the evidence and its check method. Map it to belt stages only when the criterion is real.
7. **Page and directory.** Create `src/pages/katas/<slug>.astro`, add it to `KATA_DIRECTORY`, then add the `kataCatalog` record with `href: '/katas/<slug>'`. A record never points at a page that does not exist.
8. **Tracking issue.** Record its status (Draft), maintainer role, sources opened with dates, what was run and what was not, and the next review.
9. **Validate.** Run `npm run taxonomy:lock` (it records the new kata ID, route and vocabulary), then `npx vitest run`, `npm run check` and `npm run build`. Passing proves only that the structure is valid. Publication still needs the review listed under "Starter catalog" in [kata-metadata.md](kata-metadata.md#starter-catalog).

Adding a recipe, constraint or pathway follows step 3 alone: add the ID to its registry, then use it, then run `npm run taxonomy:lock`.

A run of specializations for one field, with real files and CI-computed checks, is a sector pathway; follow [sector-packs.md](sector-packs.md) for it.

## Checklist: add a kata family

A family is a set of katas that share an ID prefix and a purpose, such as the foundation family `FND-*` (#85, [foundation-katas.md](foundation-katas.md)) or the fixture family `FIXFND-*`.

1. Choose a prefix that is not in `src/data/taxonomy-lock.json` under `kata-id`, including retired IDs. A prefix is upper-case letters and digits; numbering starts at `001`.
2. Write the first record. A family of foundations needs no field; a family of specializations names its fields and at least one foundation.
3. Choose route slugs that describe the practice (`/katas/fixture-foundation-define-outcome`), not the ID. A slug may change later with a move; the ID may not.
4. Records that have no page yet stay staged, like `stagedFoundationKatas`, and are not in `kataCatalog` or `KATA_DIRECTORY`.
5. Run `npm run taxonomy:lock`. The IDs are now reserved, even for a staged record.

## Checklist: add a relationship

A relationship links a kata to another dimension (a field, an outcome, a foundation). There are two cases.

**Using an existing relationship** is data. Add the ID to the kata's list, for example `crossFieldTransfers: [manufacturing]` or `foundationKataIds: [FND-001]`. The validator checks that the target exists and, for foundations, that it is a foundation and makes no cycle.

**Adding a new kind of relationship** (a new list on every kata) changes the contract, so it goes through the contract maintainers on #81 or a successor:

1. Add the list to `kataMetadataSchema` with a default and its reason in `KATA_DEFAULTS` (`src/lib/kata-schema.ts`). `tests/kata-schema.test.ts` fails if the two drift apart.
2. Add it to `listDimensions` so a repeated ID is rejected.
3. If it points at a registry, add the registry to `KataReferences` and a row to the checks in `validateKataCatalog` (`src/lib/kata-catalog.ts`).
4. If the registry is new, add its kind to `IDENTIFIER_KINDS`, `MOVABLE_KINDS` and `RETIRABLE_KINDS` in `src/lib/taxonomy-identifiers.ts`, collect it in `liveIdentifiers`, and run `npm run taxonomy:lock`.
5. Document the field in [kata-metadata.md](kata-metadata.md) and in the field dictionary above, then add a fixture that uses it.

## Rename or retire an identifier

Rename only when the old identifier is misleading or wrong, never for taste. Every rename is a move in the ledger.

1. **Decide it on an issue.** The ledger entry names that issue and says why.
2. **Change the data.** Rename the ID in its registry, then update every reference to it. For a route, rename the recipe file or the page under `src/pages/katas/`, and update every `href` that links it (`kataCatalog`, `KATA_DIRECTORY`, fixtures, pages). The validator lists every reference you missed, naming the kata.
3. **Record the move** in `src/data/taxonomy-moves.json`:

   ```json
   { "kind": "kata-route", "from": "/katas/old-slug", "to": "/katas/new-slug", "issue": 82, "date": "2026-11-21", "reason": "Why it moved" }
   ```

   For a route, this entry is the redirect: the build writes a page at the old route that sends the visitor on, marked `noindex`.
4. **Retire instead of moving** when nothing replaces the identifier: `{ "kind": "outcome", "id": "old-outcome", "issue": 82, "date": "2026-11-21", "reason": "..." }` in `retired`. A retired identifier can never be used again. A kata ID can only be retired, never moved. A route can only be moved: a withdrawn kata keeps its page with a notice (see "Status" above), or its route moves to an alternative.
5. **Check saved progress.** If anything saved on the device names the identifier, migrate it in the same MR (see "Saved progress" below). Today nothing does.
6. Run `npm run taxonomy:lock` (it adds the new identifier, and keeps the old one), `npx vitest run` and `npm run check`.

## Worked example: renaming the FIXFND fixture family's routes

In #82 the fixture foundation family took descriptive route slugs. This change is real, on the live site, and CI checks it on every pipeline:

| Kata ID (unchanged) | Old route (now a redirect) | New route |
| --- | --- | --- |
| FIXFND-001 | `/katas/fixture-fixfnd-001` | `/katas/fixture-foundation-define-outcome` |
| FIXFND-002 | `/katas/fixture-fixfnd-002` | `/katas/fixture-foundation-compare-stack` |
| FIXFND-003 | none (no page) | `/katas/fixture-foundation-check-sources` (fixture record only) |

What changed, step by step:

1. The two recipe files were renamed (`git mv`) to `fixture-foundation-define-outcome.yaml` and `fixture-foundation-compare-stack.yaml`. Their `metadata.id` did not change.
2. The fixture records in `tests/fixtures/kata-sectors.ts` take their slugs from `FOUNDATION_FIXTURE_SLUGS`, so every `href` follows. `tests/kata-recipes.test.ts` checks that each fixture page's `href` equals its record's.
3. Two `kata-route` moves were added to `src/data/taxonomy-moves.json`. Before they were added, the build and `tests/taxonomy-identifiers.test.ts` failed with "kata-route /katas/fixture-fixfnd-001 was published and its page is gone".
4. `npm run taxonomy:lock` added the two new routes. The old ones stay in the lock for good.

The proof is in `tests/kata-taxonomy-migration.test.ts` ("worked migration"), with the browser side in `e2e/taxonomy-redirects.spec.ts`:

- one move for each published route of the family, decided on #82;
- the renamed records keep their kata IDs, under the new slugs;
- no page is left at an old route, and each old route resolves to a page that exists;
- no record, catalog entry or directory entry links an old route;
- a representative device saved before the rename (Train progress, lessons, a checklist, the self-assessment and the belt journal) exports the same keys and loads with the site's own parsers;
- in a browser, each old route lands on its new page, and the redirect page is `noindex`.

## Migration from the existing collections

The taxonomy is added on top of what exists. Adding it renamed and moved nothing, so no data migration was needed. The only route moves since then are in the ledger (`src/data/taxonomy-moves.json`), starting with the worked example above.

| Existing item | Identifier | Where it joins the taxonomy | Change |
| --- | --- | --- | --- |
| Kata pages | route `/katas/<slug>` | `href` of a `kataCatalog` record | none; routes stay |
| Kata discovery directory | `KATA_DIRECTORY` (`src/data/kata-directory.ts`) | the discovery list of kata pages; an entry needs no taxonomy record | none; every listed route keeps its page |
| Starter taxonomy records | `PRACTICE-001` to `PRACTICE-008` | `kataCatalog` | IDs kept; they never take planned `FND-*` or `UX-*` IDs |
| Tracks | slug in `src/content/tracks`, URL `/library/tracks/<slug>/` | `pathwayIds`; `fields[].trackHref` | none; URLs stay ([track-urls.md](track-urls.md)) |
| Lessons | library path without `.md`, URL `/library/<path>/` | through their track (`pathwayIds`) | none |
| Resources | `publisher/resource` (#23) | `externalResources`, `standards[].sourceResourceId` | none; one catalogue, no copies |
| Search groups | derived from the URL (`src/lib/search-groups.ts`) | katas group by their `/katas/` route | none; search needs no taxonomy metadata |
| Train page progress | `dojo-progress-v1`, `{ completed: { moduleId: date } }` | not keyed by kata ID | none |
| Lesson progress | `dojo:lessons`, version 1, keyed by lesson path | not keyed by kata ID | none |
| Checklists and drafts | `dojo:checklist:<pageId>`, `dojo:draft:<pageId>` | page IDs, not kata IDs | none |
| Belt evidence and self-assessment | `dojo:belt-evidence`, `dojo:self-assessment:track-a` | belt stages match `BELT_STAGES` | none |

The one deliberate contract change is in #81: free-text `constraints` became registry-checked `constraintIds`. No published record used `constraints`, so no record needed rewriting.

`tests/kata-taxonomy-migration.test.ts` checks this with real repository data and representative saved values:

- every `kataCatalog` and `KATA_DIRECTORY` route has its page, and every field's track exists;
- the storage keys above are unchanged;
- a saved Train record (`developer-week-1`, `developer-week-2`) still loads;
- a saved lesson record (a week lesson and a robotics track lesson) still names existing lessons;
- every Train module still points at an existing lesson.

### Saved progress

Progress lives only on the learner's device (`src/lib/storage.ts`). The Dojo writes these keys, and no key or value is derived from a kata ID, a kata route or a taxonomy ID:

| Key | Keyed by | Written by |
| --- | --- | --- |
| `dojo-progress-v1` | Train module ID (`src/lib/progress.ts`) | `ProgressPanel.astro` |
| `dojo:lessons` | library lesson path | `LessonDone.astro` |
| `dojo:checklist:<page>` | library page ID | `ChecklistTool.astro` |
| `dojo:draft:<page>` | library page ID | `TemplateForm.astro` |
| `dojo:self-assessment:track-a` | fixed name | `SelfAssessment.astro` |
| `dojo:belt-evidence` | the belt journal's own field list (`software`, `ux`, `bim`, ...), not `src/lib/fields.ts` | `BeltJourney.astro` |
| `dojo-theme` | display preference, not progress | `ThemeToggle.astro` |

So moving a kata route or renaming a field, outcome or other vocabulary ID leaves saved progress as it is. `tests/kata-taxonomy-migration.test.ts` enforces this. It fails when a component not in this table starts saving on the device, when a kata page imports one of these components, and when the belt journal's saved field keys change.

If a future kata page does save progress, key it by the **kata ID**, which never moves, and never by its route. Add the component to the inventory in the test and to this table in the same MR.

If a lesson path, track or storage key ever has to change, follow [track-urls.md](track-urls.md#if-a-track-really-must-change). Migrate the saved value in the same MR with the store's `migrate` option (`LoadOptions` in `src/lib/storage.ts`), and extend the migration test with the old value.
