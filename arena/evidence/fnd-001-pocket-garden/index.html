Dojo experiment · ARN-001 · 20 November 2026

Pocket Garden prototype: change the instructions, then the model

On one small prototype task, what changes when only the instructions change, or only the model?

  2. Evidence records

Last checked 20 November 2026; marked stale after 20 February 2027.

Compares: Instructions, Model, Harness, Skill, Tool or integration, Delegation. Field: Software and digital products. This is not a general ranking; see the scope below.

Part of the kata Build a working prototype, then change one stack variable (FND-001), where you can run it yourself.

Task and rubric

Build Pocket Garden, a one-file page with three plant cards, sun and shade filters, and a "Mark as planted" toggle that resets on reload, from a fixed brief. No files, data or context beyond the prompt.

  • Prompt A, the task brief
  • Prompt B, the brief plus a request to compare the draft against it and list uncertainty
  • The Dojo's reference page, which passes every check (a target, not a result)

Outcome measured: A working single-file web prototype (Pocket Garden) built from a fixed brief. Rubric: Pocket Garden checks. Fourteen functional, accessibility and honesty checks made by an independent browser checker that never reads the assistant's own checklist.

Method and how to reproduce it

Three arms, three repetitions each. Repetition r of every arm started at the same moment, so time of day and service load fell on all arms alike. Each run was a new CLI process in a new, empty folder. Every saved response was checked by the same browser checker; a run that failed a check got one correction round in a fresh session, checked again.

Runs per arm: 3

  1. Install Claude Code from its official quickstart and sign in. The recorded runs used version 2.1.329; a different version is a different stack, so record yours.
  2. For each run, open a new empty folder and send the prompt file on standard input: claude -p --model <model> --effort high --setting-sources "" --strict-mcp-config --tools "" --no-session-persistence --output-format json < A.txt
  3. Use claude-sonnet-5-5 with prompt A (baseline), claude-sonnet-5-5 with prompt B (instructions) and claude-haiku-5-5 with prompt A (model). Start repetition r of every arm together, three repetitions each.
  4. Save each JSON answer, extract the one HTML code block and check it against every check below in a browser at desktop width and at 390 px, including an axe scan for WCAG A and AA.
  5. Compare your record with the published run files and results.json. Models are sampled and change, so a different number is a new observation, not a failed reproduction.

What it shows: No improvement was seen. Every failure in both arms was the same check (pressed-state). One failure in three runs against two in three is well within run-to-run variation, so this does not show that the self-review request makes results worse either.

Confounders:

  • Sampling: the same prompt gives different files on each run.
  • Three runs per arm cannot detect a small effect.
  • The self-review is unobservable: only the final file is checked.

What it shows: On this task and rubric the smaller model passed every check in all three runs, at about a twelfth of the list cost and in about the same time. Three runs on one small task are an observation to repeat, not a benchmark.

Confounders:

  • Sampling, as above.
  • The effort setting "high" may not mean the same amount of reasoning on both models.
  • The rubric tests a small, well-known task; it says nothing about harder work.

Harness: proposed, not run

Change: The same prompt and model in another harness, such as a phone or browser chat app or another CLI.

Held constant: Prompt A; The model, where the app lets you choose it; A fresh session with no attachments.

Proposed, not run. No results. Not run by the Dojo. A chat app run cannot be recorded with versions and cost the way the CLI run is; a learner can run it and record "not shown" honestly.

Confounders:

  • Apps add their own system prompts, memory and tools, often hidden.
  • Model version and cost are often not shown.

  • A skill aimed at the one check that failed would overfit this rubric; test it on an unseen task too.

Tool or integration: proposed, not run

Change: Let the builder open its own file in a browser, for example through an authorized Playwright MCP server, before answering.

Held constant: Harness, model, prompt A and empty context; only the tool permission changes.

Proposed, not run. No results. Not run. No browser tool has been authorized and reviewed for this exercise.

Confounders:

  • The agent then tests its own work; keep the independent checker separate.
  • More turns, time and cost: measure them.
  • It needs an explicit, reviewed permission set.

Delegation: proposed, not run

Change: A builder agent plus a separate reviewer agent that reads the brief and the file and sends back findings once.

Held constant: Harness, model and prompt A for the builder.

Proposed, not run. No results. Not run. The delegate-and-review kata teaches the pattern by hand; no recorded delegation run exists.

Confounders:

  • Delegation adds a correction round; compare it with a single agent that also gets one correction round.
  • On a three-card page the extra role may cost more than it finds.

Intervals are 95% Wilson score intervals. With three runs per arm they are wide: read the counts, not a winner.

Limitations and scope

  • Three runs per arm, one task, one date and one harness version.
  • Costs are list-price figures reported by the CLI, not an invoice; a subscription bills differently and was not measured.
  • The checker tests only the fourteen listed behaviours. The accessibility checks are not a WCAG conformance claim for any page.
  • The no-test-claim check is a text heuristic; read its matches in the results file.
  • The brief asks for both a changing label and a pressed state, which the WAI-ARIA button pattern advises against combining. All three failures were on that check.

Scope: What happened on this one small prototype task, with this rubric and these versions, on 2026-11-20. It is not a ranking of models, prompts or harnesses, and it says nothing about harder or different work.
