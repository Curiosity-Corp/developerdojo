Dojo experiment · ARN-003 · 21 November 2026

Pocket Garden prototype: the same model and prompt in two harnesses

On one small prototype task, what changes when only the harness changes, with the same model, effort, prompt, endpoint and no tools?

  1. The Arena
  2. Evidence records
  3. ARN-003

Run by Developer Dojo on 21 November 2026. Every number below is computed from the published run files and check results.

Last checked 21 November 2026; marked stale after 21 February 2027.

Compares: Harness. Field: Software and digital products. This is not a general ranking; see the scope below.

Part of the kata Build a working prototype, then change one stack variable (FND-001), where you can run it yourself.

Task and rubric

Build Pocket Garden, a one-file page with three plant cards, sun and shade filters, and a "Mark as planted" toggle that resets on reload, from a fixed brief. The same brief as the FND-001 baseline (prompt A).

  • Prompt A, the task brief (byte for byte the FND-001 prompt A)
  • The Qwen Code settings file used for every Qwen Code run (model, endpoint and placeholder key are filled in per run)
  • The Dojo's reference page, which passes every check (a target, not a result)

Outcome measured: A working single-file web prototype (Pocket Garden) built from a fixed brief. Rubric: Pocket Garden checks. Fourteen functional, accessibility and honesty checks made by an independent browser checker that never reads the assistant's own checklist.

Method and how to reproduce it

Two arms, three repetitions each. Repetition r of both arms started at the same moment. Each run was a new harness process with a new, empty home folder and working folder, so no sign-in, settings, memory or history was visible to it. Both harnesses sent their requests through one local recording relay to the same Anthropic-compatible endpoint (OpenRouter) with the same account, the serving provider pinned to Amazon Bedrock and no fallback. The relay held the key, recorded what each harness sent (model, effort, thinking mode, output limit, system prompt size and hash, tool names, prompt hash) and what came back (served model, token usage, billed cost). Time is the wall-clock time of the harness process, measured the same way for both arms. Every saved response was checked by the same browser checker as ARN-001; a run that failed a check got one correction round in a fresh process of the same harness, checked again.

Runs per arm: 3

  1. Install Claude Code from its official quickstart and Qwen Code from its repository, and record both versions. The recorded runs used Claude Code 2.1.330 and Qwen Code 0.28.0; a different version is a different stack.
  2. Create an OpenRouter API key and pin the serving provider for Claude Sonnet 5.5 (provider routing), so both harnesses reach the same provider. Give the key to the harnesses only through their documented environment variables.
  3. Claude Code, in a new empty folder with a new empty home and configuration folder: set ANTHROPIC_BASE_URL to the OpenRouter Anthropic endpoint and ANTHROPIC_AUTH_TOKEN to your key, then run claude -p --model anthropic/claude-sonnet-5.5 --effort high --setting-sources "" --strict-mcp-config --tools "" --no-session-persistence --output-format json < A.txt
  4. Qwen Code, in a new empty folder with a new empty home: copy qwen-settings.json to .qwen/settings.json in that home and fill in the model and endpoint, set ANTHROPIC_BASE_URL and ANTHROPIC_API_KEY, then run qwen --safe-mode --chat-recording false --exclude-tools <every built-in tool&gt; --output-format json < A.txt. Check its first output line: the tool list must be empty.
  5. Start repetition r of both arms together, three repetitions each. Save each answer, extract the one HTML code block and check it against every check below in a browser at desktop width and at 390 px, including an axe scan for WCAG A and AA.
  6. Compare your record with the published run files and results.json. Models are sampled and change, so a different number is a new observation, not a failed reproduction.

What it shows: Both harnesses produced pages that the checker passed on most checks. The failures were the pressed-state check in both arms, plus one colour-contrast failure in one Claude Code run; after one correction round every corrected run in both arms passed every check. Two of three against one of three first-attempt runs passing every check is within run-to-run variation. Billed cost was lower for Qwen Code in each of the three paired repetitions, which the request records attribute mainly to prompt caching. This is what happened on one small task with these versions on one date; it does not show that either harness gives better pages.

Confounders:

  • Each harness adds its own hidden system prompt. Qwen Code's was more than twice as long as Claude Code's and was the same in every run; Claude Code's changed from run to run.
  • Both harnesses add environment details (date or working folder, operating system, shell). Claude Code sent prompt A unchanged as the first message and added its details as a separate system turn; Qwen Code put its details in a block in front of prompt A, in the same message.
  • The harnesses asked for different output limits and different thinking display settings, and Claude Code sent more beta feature flags. These belong to the harness, so they are part of what changed.
  • Prompt caching: Qwen Code's unchanged system prompt was read from the provider's cache on every run, including the first, which followed a short setup check minutes earlier; Claude Code wrote its changed system prompt to the cache each time. That lowers Qwen Code's billed cost and is a harness behaviour, not a price difference.
  • Sampling: the same prompt gives different files on each run, and three runs per arm cannot detect a small effect.

Intervals are 95% Wilson score intervals. With three runs per arm they are wide: read the counts, not a winner.

Limitations and scope

  • Three runs per arm, one task, one date and one version of each harness.
  • The model was reached through OpenRouter and served by Amazon Bedrock, not through Anthropic's own endpoint as in ARN-001, and with an API key instead of a subscription sign-in, so neither arm is directly comparable with ARN-001's numbers.
  • Costs are what OpenRouter billed for each request (reported with the response), the same basis in both arms. Claude Code's own cost estimate is kept in each run file as harnessReportedCostUsd; Qwen Code does not report a cost.
  • Time is the wall-clock time of the whole harness process, including start-up, so it is not the model's generation time. Each harness's own reported duration is kept in the run files.
  • Qwen Code was run in safe mode with every built-in tool excluded. Without safe mode it made a second, background request that carried tools, so its default behaviour is not what was measured.
  • The relay records each request's system prompt and first message only as a length and a SHA-256 hash, not as text, so the hidden prompts are described, not published.
  • The checker tests only the fourteen listed behaviours. The accessibility checks are not a WCAG conformance claim for any page; the no-test-claim check is a text heuristic.

Scope: What happened on this one small prototype task, with this rubric, these two harness versions and this endpoint, on 2026-11-21. It is not a ranking of harnesses, and it says nothing about tasks that use tools, files or more than one turn, where harnesses differ most.
