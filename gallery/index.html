One prototype brief, three stacks, twelve checked runs

The FND-001 comparison record. The same prototype brief went to an AI coding assistant with one variable changed at a time (the instruction, then the model). An independent browser checker scored every response, and failed runs were corrected and checked again.

  • Read the evidence notes
  • Every check result (JSON)
  • Open one checked run
Artifact
Run records (JSON), the prompts sent, the HTML of every run and the check results. The actual file, served here. Open it, inspect it and edit a copy.
Made by
Developer Dojo maintainers, November 20, 2026. Claude Code 2.1.329 in print mode with claude-sonnet-5-5 and claude-haiku-5-5, no tools and no inherited configuration. The runner and checker scripts are published with the site source.
Source
Prompt A from the "Make a clickable prototype" kata. Nine first runs and three corrections, all on 2026-11-20.
Rights
Dojo material under the MIT licence. The model responses are kept unedited as evidence. Read the terms
Checked
Every pipeline re-runs the browser checker on all twelve stored responses and the reference, and fails if any recorded result changes. The counts, times and costs in the record are recomputed from the run files. Negative controls show the checker fails broken files. See the evidence
Not checked
Three runs per arm on one task, one date and one harness version: observations to repeat, not a benchmark. Costs are list prices reported by the tool, not an invoice. The harness comparison is a separate record with its own runs; the skill, tool and delegation comparisons were designed but not run.
Outcome
Compare two AI stacks fairly
Fields
Software and digital products

Make your own

  1. RecipeBuild a working prototype, then change one stack variable
  2. Exercise Make a clickable prototype
  3. QA
    • Automated check: Every response is scored by an independent browser checker that never reads the assistant's own checklist. CI re-runs it on the stored responses and fails if a recorded result changes.
    • Self-check: The learner records harness, model, versions, settings, every check result, time and cost (or "not shown") for each run, before reading the other arm.
    • Peer review: A second person reads the learner's record and repeats at least two checks on the saved HTML.
  4. Belt
    • Practice: Runs the smoke test and the baseline, records harness, model and versions (or "not shown"), and scores the saved HTML against every rubric check.
    • Adapt: Changes exactly one variable, keeps the rest as stable as the tools allow, repeats each arm at least three times and names the confounders it could not remove.
    • Demonstrate: Completes the unseen transfer challenge: writes the observable checks before prompting, runs a controlled comparison and reports failures and corrections without overstating the result.
  5. FoundationsThis is a shared foundation itself: every field builds on it.

BMI-for-age percentiles and categories for six fictional children, checked against CDC’s growth charts

The HLT-002 and HLT-003 worked example. CDC’s two BMI-for-age data files are checked against CDC’s worked examples and every printed column, then six fictional children are scored with the LMS method and, above the 95th percentile, the extended method, and placed in CDC’s child and teen BMI categories. Practice only, not a clinical assessment.

Artifact
Scores per child (CSV and JSON), the reference checks (JSON) and a one-page summary (Markdown). The actual file, served here. Open it, inspect it and edit a copy.
Made by
Developer Dojo maintainers (fictional children, script and results); CDC National Center for Health Statistics (data files, method and categories), November 26, 2026. A Python 3.12 script with no packages, published next to the results, using the methods on CDC’s growth chart pages.
Source
CDC’s BMI-for-age data files of the 2000 and 2022 Extended growth charts, its Extended BMI-for-age data files page and its Child and teen BMI categories page, read on 2026-11-26.
