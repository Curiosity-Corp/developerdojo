Infrastructure as code

Describe cloud infrastructure in files, review the plan before anything changes, and judge what agents write with Terraform and OpenTofu.

In short

This track is for product managers, founders and developers. You will ask agents to change cloud resources. You do not need to write code. Infrastructure as code means you describe servers, networks and permissions in files in git. A tool reads the files and makes the change. You will read a plan before anything changes. You will find what will be added, changed or destroyed.

You will learn why the tool’s state must be protected. You will direct an agent to write the files in a merge request. You will also check for drift. You will set what agents may do, and ask about cost and security. Nothing real changes until a person has read the plan and approved it.

Key words

  • IaC (infrastructure as code): Cloud setup written as files in git.
  • Plan (infrastructure as code): A preview of what the tool will add, change or destroy. You read it before you approve.
  • State (infrastructure as code): The tool’s memory of what it has built. Protect it, and keep one shared copy.
  • Drift: Any difference between desired state and actual state.
  • Merge request (MR): A proposal to add a change to the main branch. Also called a pull request.

Infrastructure as code (IaC) means that the servers, networks, databases and permissions your product runs on are described in text files, kept in git, and created by a tool reading those files. Instead of clicking through a cloud console, you write what you want. The tool compares it with what exists, shows you the difference, and, once you approve, makes the change.

For someone directing AI agents this is the safest way to let them near infrastructure. An agent can write a file, and a person can read the file and the plan before anything real changes. The alternative, an agent clicking or typing live commands, leaves no record and no review.

This track gives you enough depth to direct and judge: to read a file, read a plan, notice that something will be destroyed, and ask whether the change is safe.

Who this is for

Product managers, founders and developers who will ask agents to create or change cloud resources. You should know the basic cloud parts from Cloud platforms and how a merge request works from Git and GitLab. You do not need to write code.

What you will be able to do

  • Explain declarative description: you state the end result, the tool works out the steps.
  • Read a short Terraform or OpenTofu file: providers, resources, variables, outputs.
  • Read a plan and pick out the lines that matter: what is added, changed, and above all destroyed or replaced.
  • Explain state: the tool’s memory of what it has built, why it must be protected, and why it must be shared.
  • Explain modules as reusable packages, and environments as separate copies.
  • Run the loop in a pipeline: plan in the merge request, apply after approval, detect drift.
  • Ask security and cost questions about infrastructure code, and set what agents may do.

How it maps to the program

The Master Developer program says everything is code, production changes only through reviewed merge requests, and drift is a defect. See Everything as code, GitOps and drift. This track is how that rule is applied to cloud resources; the Kubernetes and GitOps track applies it to what runs on a cluster.

Terraform and OpenTofu

Terraform is the best-known tool, made by HashiCorp. OpenTofu is an open source, community-governed fork that uses the same language and ideas. The Way prefers open source first, so the examples work with either, and the lessons say “the tool”. Check the current licence terms of any tool before you build a business on it; see Open source licences. Pulumi, the cloud providers’ own template languages and others exist, and the ideas carry over.

The running example

TrailMug, the fictional reusable-cup product, needs a bucket for its site, a small database and a few permissions. Maya directs agents to write the code, and reads every plan. People and numbers are invented.

Time needed

About 75 to 90 minutes per lesson, so six hours for the track. Hands-on work needs a free or throwaway cloud account with a budget alert, or the tool’s local practice mode; never your production account. Each exercise ends with your spec, your agent brief and your review notes in git.

Pair it with

Cloud platforms before it, and CI/CD alongside it. Security fundamentals after it for the defensive view.
