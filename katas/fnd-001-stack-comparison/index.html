Foundation kata · FND-001

Build a working prototype, then change one stack variable

Start from a working prototype. Have an AI assistant rebuild it from a fixed brief, score the result with an independent rubric, then change exactly one part of the stack and compare.

The outcome

A working single-file web prototype (Pocket Garden), rebuilt by an AI assistant from a fixed brief and scored by an independent rubric, plus a comparison record that shows what changed when exactly one part of the stack changed.

For: Anyone who works with an AI assistant or coding agent and wants to know whether a change to their setup (harness, model, instructions, a skill, a tool or agent roles) actually helps.

Done when

  • Your saved HTML is scored against all 14 checks, by hand or with a checker, and every result is written down.
  • You changed exactly one part of the stack, ran each arm at least three times, and recorded versions, time and cost, writing "not shown" where your tool hides them.
  • Your record names the confounders you could not remove and says what the result does not show.
  • You completed the unseen transfer challenge, with checks you wrote before prompting.

You make: Prototype, Comparison record. Outcome: Stack comparison.

Showcase and provenance

Pocket Garden, the Dojo's working single-file prototype: three plant cards, sun and shade filters, and a planted toggle that resets on reload. It passes all 14 rubric checks, and CI checks it again in every pipeline. It is the target the comparison aims at, not a result of it.

Stack recipes

  • Assistant and browser
  • Claude code print no tools

Why this stack

Print mode with no tools and no inherited configuration is the smallest stack a learner can rebuild exactly. It removes the hidden variables (memory, skills, MCP servers, project instructions) that make two chat sessions hard to compare.

Alternatives

  • Phone or browser chat app (the starting path in the stack workbench). Easiest to reach, but versions, hidden settings and cost are usually not shown. Not tested for this recipe.
  • Interactive CLI session with tools. The agent could open and test its own file, which changes what is being compared (see the proposed tool comparison). Not tested for this recipe.
  • Qwen Code 0.28.0, another CLI harness, on the same model through the same endpoint. Measured as the harness comparison (ARN-003). It adds its own hidden system prompt, so do not mix harnesses inside any other comparison. Tested for this recipe.

Agents and review gates

  1. Builder

    One assistant session per run writes the complete HTML from the prompt.

    Review gate: Nothing counts until the Checker has scored the saved HTML.

  2. Checker

    Loads the saved HTML in a browser and scores the 14 checks, at desktop width and at 390 px. It never reads the Builder's checklist. In the Dojo runs this was a deterministic script, not a model.

    Depends on: Builder

    Review gate: A failed check sends the file back to a fresh Builder session once, with the Checker's observations; the corrected file is scored again.

  3. Reviewer

    The learner, and if possible a peer, read the results, decide whether a difference is real and name the confounders.

    Depends on: Checker

    Review gate: Repeats at least two checks on the saved HTML before the record is shared.

Setup and smoke test

  1. Phone or browser path: open any assistant you can use, start a fresh chat, paste prompt A and save the complete answer. Paste the HTML into the preview in the stack workbench. Record the versions and the cost as "not shown" if the app hides them.
  2. CLI path: install Claude Code from the official quickstart (https://code.claude.com/docs/en/quickstart) and sign in. Read your plan and the cost guidance first. Record the output of claude --version.
  3. For each run, open a new empty folder and send the prompt file on standard input: claude -p --model claude-sonnet-5-5 --effort high --setting-sources "" --strict-mcp-config --tools "" --no-session-persistence --output-format json < A.txt
  4. Save each answer unedited. Copy the one HTML code block into a file, open it in a desktop browser and score it with the check sheet (download below).

Sign-in and access: Sign in to your own assistant account or Claude Code plan. The Dojo gives no access. No key or token belongs in a prompt, a record or a shared file.

Execution and handoffs

  1. Builder: Runs the prompt in a fresh session, three repetitions per arm. Repetition r of every arm starts at the same moment, so time of day and service load fall on all arms alike. Hand-off: The complete answer, saved unedited as a run file.
  2. Checker: Copies out the one HTML code block and scores all 14 checks at desktop width and at 390 px. Hand-off: One result per check per run.
  3. Builder: For each run that failed a check, one correction round in a fresh session, with the run's HTML and the Checker's observations (the correction prompt). Hand-off: The corrected file, scored again by the Checker.
  4. Reviewer: Compares the arms on the shared measures (runs passing every check, time, and cost or "not shown") and writes the reading with its confounders. Hand-off: The comparison record.

Failures and corrections

  • Observed: Instructions and model comparison (ARN-001): pressed-state failed in three of nine first runs (baseline-r2, instructions-r1 and instructions-r3). The plant buttons changed their label but exposed no aria-pressed. No other check failed. Correction: One correction round each, in a fresh session with the checker's observation. All three corrected files passed every check.
  • Observed: Harness comparison (ARN-003): pressed-state failed in claude-code-r1, claude-code-r3 and qwen-code-r3, and claude-code-r3 also failed axe-serious (colour contrast). Correction: One correction round each, in a fresh process of the same harness. All three corrected files passed every check.

Adapt it

  • Software (run by the Dojo, this recipe). A single-file web prototype scored by an independent browser checker; the controlled comparisons above.
  • Visual or document (proposed, not run by the Dojo). Generate a one-page event poster from a fixed brief, check its text, contrast ratio and print size against written criteria, and change only the model.
  • 3D or BIM (proposed, not run by the Dojo). Ask an assistant to list the walls and their types in the buildingSMART sample IFC file used in the "Investigate a real IFC model" kata, check the list against the file, and change only the instructions.
  • A phone or browser app instead of the CLI (proposed, not run by the Dojo). Use the same prompts and check sheet, and record versions and cost as "not shown" where the app hides them. This is a harness change, so do not mix it into another comparison.

Unseen Randori

Unseen challenge: a one-file "Tool Library" page lists five shared tools (two power tools, three hand tools), filters them by type, and lets the user mark a tool "Borrowed" and back. A borrowed tool shows who has it, using a name typed into a field that must have a visible label.

Constraints

  • Write at least eight observable checks before you prompt.
  • Change one variable you have not changed before, with three runs per arm.
  • Fictional names and data only.
  • Not run by the Dojo, so there is no reference answer. Your checks are the rubric.

How it is judged: A reviewer reads your checks, repeats at least two of them on your saved HTML, and confirms that your record reports failures and corrections without overstating the result. The changed data, the form field and the extra state mean a stack tuned to Pocket Garden can fail it.

Belt evidence

Belt stages are proposed practice stages, not issued credentials. Evidence below is what a reviewer would look for; it is not a record that anyone has shown it.

Evidence a reviewer looks for

  • Every response is scored by an independent browser checker that never reads the assistant's own checklist. CI re-runs it on the stored responses and fails if a recorded result changes. (Automated check, against Web Content Accessibility Guidelines (WCAG))
  • The learner records harness, model, versions, settings, every check result, time and cost (or "not shown") for each run, before reading the other arm. (Self-check)
  • A second person reads the learner's record and repeats at least two checks on the saved HTML. (Peer review)

Belt criteria

  • Practice: Runs the smoke test and the baseline, records harness, model and versions (or "not shown"), and scores the saved HTML against every rubric check.
  • Adapt: Changes exactly one variable, keeps the rest as stable as the tools allow, repeats each arm at least three times and names the confounders it could not remove.
  • Demonstrate: Completes the unseen transfer challenge: writes the observable checks before prompting, runs a controlled comparison and reports failures and corrections without overstating the result.

Maintenance and caveats

Review cadence: Quarterly, and whenever Claude Code changes major version or its print-mode flags change, a model named here is retired or renamed, a rubric check stops passing on the reference, or a learner reports a different smoke-test result.

  • Model behaviour, prices and CLI flags change. These results are from 20 and 21 November 2026; run them again before you rely on them.
  • Three runs per arm on one small task are observations to repeat, not effects, and not a ranking of models, prompts or harnesses.
  • Costs are list prices reported by the CLI (ARN-001) or what the endpoint billed (ARN-003), not an invoice. A subscription bills differently and was not measured.
  • The accessibility checks are practice checks, not a WCAG conformance claim for any page.
  • The brief asks for both a changing label and a pressed state, which the WAI-ARIA button pattern (https://www.w3.org/WAI/ARIA/apg/patterns/button/) advises against combining. Every pressed-state failure was on that check, so question the brief in your reflection.
