The outcome

A short fidelity report for your screens that says, for each state, which properties of the build match the design, which do not, and what was not measured.

For: Learners who have a high-fidelity design and a built page of the same screens (UX-004 and UX-005).

Done when

  • Every colour, type size, weight, corner and border in the design is a token value
  • For each state, the build’s computed colour, type size and weight, border and control height are compared with the design
  • Every difference is listed with the state, the element and both values
  • What was not measured (for example pixels, hover, focus styles or the dark theme) is written down as not measured, not as passed

You make: Fidelity report. Outcome: Check visual fidelity.

The Dojo’s worked example, made by the maintainers rather than by a learner: the Pocket Invoice fidelity report and the style guide page it is checked against.

Why this stack

A fidelity check is only as good as its list of what it compared. Penpot’s inspect mode and the browser’s inspector show the same properties side by side, and the Dojo’s script and browser tests show one way to compare them automatically.

Alternatives

  • Pixel comparison (screenshot diff). Catches layout drift the property comparison misses, but fails on font rendering differences between machines and says nothing about which token is wrong. Not run for this pathway. Not tested for this recipe.
  • Figma Dev Mode. Shows properties and code for a design, on a paid Dev or Full seat (figma.com/pricing, checked 2026-11-20). Not tried for this pathway. Not tested for this recipe.

Agents and review gates

  1. Drafting assistant

    Turns two lists of properties (design and build) for one state into a table of matches and differences.

    Review gate: You check every row against the inspector before it goes into the report.

  2. Reviewer

    Picks three states, compares them in an inspector without reading your report first, and lists differences.

    Depends on: Drafting assistant

    Review gate: A difference counts only when the reviewer names the state, the element and both values.

Setup and smoke test

  1. Open the Pocket Invoice style guide page and the working example in two tabs.
  2. Open your browser’s inspector on a button in each and compare the computed colours.

Sign-in and access: None.

Smoke test

Do
In the style guide, inspect Button/Primary.
Expect
Its background is var(--pi-color-action-primary), which resolves to the value in the token file.
Result
Passed /examples/pocket-invoice-style-guide/, compared with the token file by the site’s browser tests on every pipeline

Prompts

Copy a prompt into the assistant you use. Replace anything that does not fit your situation, and never paste private or personal data you are not allowed to share.

Compare one state

Turns two property lists into a table you can check.

You can also select and copy the text.

Practice exercise

Inspect mode (Penpot user guide). From Dev tools: inspect mode (Penpot).

Terms: Read on the publisher’s site under its terms. Credited, not copied. If a course or programme you take part in uses this exercise, follow its rules on AI assistance, and do not submit work an assistant wrote where those rules forbid it.

Execution and handoffs

  1. Learner: Read the example fidelity report and find three of its properties in the inspector. Hand-off: Collect the design and build properties for one of your own states.
  2. Drafting assistant: Compare the two lists with the prompt. Hand-off: You check each row in the inspector and fix the build or the design.
  3. Reviewer: Compare three states without your report and list differences. Hand-off: You add anything they found that your report missed, and say why it was missed.

Adapt it

  • Add a dark theme to the tokens. The comparison doubles; contrast must be checked again for every semantic colour.
  • The build uses a component library you did not design. Compare the library’s tokens with yours first, and list every value that has no token.

Belt evidence

Belt stages are proposed practice stages, not issued credentials. Evidence below is what a reviewer would look for; it is not a record that anyone has shown it.

Evidence a reviewer looks for

  • Every drawing is audited for token use, text and boundary contrast, control size and components, and the working page is compared with the high-fidelity screens in every state at 390 px and 1440 px, in the site pipeline (Automated check, against Web Content Accessibility Guidelines (WCAG))
  • A partner compares three states of your build with your design in an inspector and lists every difference they find (Peer review)

Belt criteria

  • Practice: Reads the example fidelity report and finds, in the inspector, the token behind three properties of the working page
  • Adapt: Changes one token, reruns the script, and shows the drawings and the page changing together
  • Demonstrate: Writes a fidelity report for their Randori screens that lists what was compared and what was not measured

Maintenance and caveats

Review cadence: Every six months, or when Penpot changes inspect mode

  • This recipe is a draft: the example was built and checked by the Dojo maintainers, and no learner has run it yet.
  • Not measured for the example: a pixel comparison of whole screens, hover and focus styles, the dark theme, text width in the brand font, colour-vision simulation and a review by a designer.
  • The comparison is with SVG drawings generated from the tokens, not with a file edited in Penpot or Figma; no native design-tool file was compared.
