The outcome

A new user of a fictional invoicing app reaches their first sent invoice using only the keyboard.

For: Freelancers who have never used the app, including people who navigate without a mouse.

Done when

  • Every onboarding step can be reached and completed with the keyboard alone
  • Three moderated sessions are written up, with what each participant tried
  • One finding is fixed and the before and after are shown

You make: Interactive prototype, Usability findings. Outcome: Usable onboarding.

Not available. No learner has made this outcome yet, so there is no authentic example to show.

Constraints

  • Keyboard only
  • Fictional data

Why this stack

A browser prototype and an open-source design tool keep the exercise free of installs and licences, and both can be tested with a keyboard.

Alternatives

  • Figma through an MCP server. Brings design context into an agent, but needs an account and has not been run for the Dojo. Not tested for this recipe.

Agents and review gates

  1. Designer

    Drafts the journey map and the prototype screens from the brief.

    Review gate: The learner checks every step against the done-when list before testing.

  2. Note taker

    Turns the learner's session notes into findings, one per observed problem.

    Depends on: Designer

    Review gate: The learner compares each finding with their own notes; nothing a participant did not do is added.

Setup and smoke test

  1. Open a new chat in the assistant you use.
  2. Open Penpot in a browser and create an empty practice project.
  3. Paste the first prompt and keep the answer next to the project.

Sign-in and access: Sign in to Penpot with your own account. The chat assistant needs no extra access.

Smoke test

Do
Tab through the first prototype screen from the address bar.

Focus reaches every control in reading order and is always visible.

Practice exercise

Moderated usability testing. From Using moderated usability testing (GOV.UK Service Manual).

Terms: Read on the publisher's site. GOV.UK guidance is published under the Open Government Licence v3.0 unless it says otherwise.

Execution and handoffs

  1. Designer: Draft the journey and screen list with the first prompt. Hand-off: The learner checks the draft and builds the prototype.
  2. Learner: Run three moderated sessions with keyboard-only navigation. Hand-off: Session notes go to the note taker.
  3. Note taker: Write findings from the notes with the second prompt. Hand-off: The learner fixes one finding and records the before and after.

Adapt it

  • The product becomes a patient appointment booking service. Health data rules apply; the prototype must use fictional patients only, and the findings need a privacy review.
  • Participants use a screen reader. Headings, labels and live announcements need checking as well as focus order.

Belt evidence

Belt stages are proposed practice stages, not issued credentials. Evidence below is what a reviewer would look for; it is not a record that anyone has shown it.

Evidence a reviewer looks for

  • Findings from three moderated sessions, with what each participant tried (Peer review)
  • Keyboard and contrast checks on every onboarding step (Automated check, against Web Content Accessibility Guidelines (WCAG))

Belt criteria

  • Demonstrate: Fixes one finding and shows the before and after
