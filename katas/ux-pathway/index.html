SaaS UX · Pathway

From sitemap to a tested screen.

Follow one small product, Pocket Invoice, through every UX step. Each step has a real file you can open, edit and check.

Try the working exampleStart with UX-001

01 / See the outcome

Pocket Invoice: one job, every state

The job: A freelancer sends their first invoice to a client. For: Freelancers who have never used the app, on a phone or a computer, including people who use only a keyboard.

Pocket Invoice is invented for practice. The same flow is drawn in an editable Penpot file and built as a working page, so you can compare the design and the result screen by screen.

  • Use the working example: every screen and error state, with a keyboard or a mouse.
  • Download the Penpot file (.penpot, about 0.5 MB): four pages, from sitemap to high fidelity.
  • Download the design tokens (JSON, 54 tokens, Penpot’s token format).
  • Read the Penpot import check (JSON): what was checked in Penpot, and what was not.
  • Read the accessibility and responsive QA report (Markdown): every state of the working page, from the site’s browser tests.

Screenshots from Penpot View mode, taken by the import check after the file was imported into a self-hosted Penpot 2.18.7.

02 / The sitemap

11 states, 19 ways between them

Every state is reachable from Create your workspace, and every error has a way back. Page 01 of the Penpot file draws this map; the lists below are the same flow as text.

Create a workspace

  • Create your workspace (Screen): The first screen: the fewest fields needed before the user can do real work.
  • Create your workspace: fix two problems (Error): Shows every problem at once, names how to fix each, and keeps what the user typed.

Sign in (out of scope)

  • Sign in (Outside this flow): A branch the example does not build. It says so and offers the way back, so the user is never stranded.

Invoices

  • Invoices: none yet (Empty state): The empty state explains what the screen is for and offers the one next step.
  • Invoices: one sent (Screen): The same screen as the empty state, now with the result of the journey in it.

New invoice

  • New invoice (Screen): The main task: the details a client needs to pay.
  • New invoice: fix two problems (Error): Validation errors on the main task, with the summary linked to each field.
  • Discard this invoice? (Dialog): A confirmation over the form, so a slip of the finger does not throw work away.

Check and send

  • Check the invoice (Screen): One look at everything before it goes to the client, with a way to change any of it.
  • The invoice was not sent (Error): A failure after the user pressed Send: says what happened, that nothing was sent, and what to do.

Sent

  • Invoice INV-0001 sent (Success): Confirms the outcome in words, with the number to quote, and the way back to the list.

03 / Open files and a clickable prototype

The same flow as plain files you can edit

The flow is also a JSON file. A small script with no dependencies reads it with the token file and draws the sitemap, a one-canvas journey and one greyscale 390 px screen per state as SVG, then checks the flow: 11 checks, 11 passed, 18 colour pairs among them. CI reruns it on every pipeline and fails if any file differs from the ones here. Change the flow file, run node tools/ux_pathway.mjs . out in a copy of this folder, and the drawings follow.

  • Click through the low-fidelity prototype (or in high fidelity): every state and all 19 transitions in the browser, including the dialog and the Back button.
  • Low-fidelity screens (SVG, one per state): Create your workspace, Create your workspace: fix two problems, Sign in, Invoices: none yet, New invoice, New invoice: fix two problems, Discard this invoice?, Check the invoice, The invoice was not sent, Invoice INV-0001 sent, Invoices: one sent.
  • Download the flow file (JSON) and the colour pairs it checks (JSON).
  • Download the script (JavaScript for Node.js, no packages to install).
  • Read the check summary (Markdown), the checks and the manifest (JSON, with the SHA-256 of each input).

Both Penpot and Figma document SVG as a way to bring drawings in from other tools (see the tools table below). Nobody has tried that with these files yet, so it is proposed, not run.

04 / High fidelity

A style guide, components and screens at two widths, from the same tokens

The same script also reads a small brand file and draws the style guide, a sheet of 13 components, and every state at a phone width (390 px) and a desktop width (1440 px): 22 screens. Every colour, size, weight, corner and border in them is a value from the token file. The script then audits each drawing as plain text: token use, text contrast against the shape under it, control boundaries and sizes, and whether each element of the flow is drawn as a component. Of 24 drawings, 24 passed; the lowest text contrast is 4.63:1 and the lowest control boundary 4.63:1. The site’s browser tests then measure every line of text in the screens, and click through the prototype in high fidelity.

  • Click through the prototype in high fidelity: the same links, drawn with the tokens.
  • Phone screens (SVG, 390 px): Create your workspace, Create your workspace: fix two problems, Sign in, Invoices: none yet, New invoice, New invoice: fix two problems, Discard this invoice?, Check the invoice, The invoice was not sent, Invoice INV-0001 sent, Invoices: one sent.
  • Desktop screens (SVG, 1440 px): Create your workspace, Create your workspace: fix two problems, Sign in, Invoices: none yet, New invoice, New invoice: fix two problems, Discard this invoice?, Check the invoice, The invoice was not sent, Invoice INV-0001 sent, Invoices: one sent.
  • Read the fidelity report (Markdown) or its data (JSON): each drawing, what was checked, and what was not measured.
  • Download the brand file (JSON: name, wordmark, voice, rules and layout widths), the high-fidelity script and the token reader it shares with the flow script.

05 / The steps

Six katas, in order

Each kata has a brief, prompts, the checks that prove it is done and the evidence for the checks the Dojo has run. They are drafts: the Dojo built and checked the worked example, and no learner has run them yet. Do the foundations first: Compare AI instructions and Spot a context trap.

  1. UX-001 Map a sitemap with branches and error states

    List every state, the ways in and out, and how each error recovers.

  2. UX-002 Draw low-fidelity screens and wire the flow

    Greyscale 390 px boards, one per state, clickable in Penpot View mode.

  3. UX-003 Define design tokens

    Colour, type and spacing as a JSON token file, with every pair checked for contrast.

  4. UX-004 Build components from tokens

    Buttons, fields, an error summary and a dialog, used on every high-fidelity screen.

  5. UX-005 Implement the screens and check accessibility

    A working page from the same flow and tokens, checked with axe, a keyboard and reflow at 320 px.

  6. UX-R01 UX Randori: an unseen flow with a hidden constraint

    Map and wire a flow you have not seen; a partner reveals one constraint after you start.

07 / What is checked

Verified, and not verified

Verified

  • The .penpot file imports into a self-hosted Penpot 2.18.7 with 4 pages, 11 state boards on each wireframe page, 8 components, 16 colours, 5 typographies and all 54 tokens. (evidence)
  • In Penpot View mode, a scripted browser clicked through all 19 transitions on both the low- and high-fidelity pages without an error.
  • The file is generated from the same flow and tokens as the working example; the site’s tests rebuild it on every pipeline and fail if it differs from the published copy.
  • Every text and control colour in the tokens meets its contrast ratio (4.5:1 for text, 3:1 for borders and focus), computed on every pipeline.
  • The working example is driven through every state in the site’s browser tests, with axe checks for WCAG A and AA, reflow at 320 px, and keyboard and dialog focus. (evidence)
  • On every pipeline, CI reruns the flow script, redraws the sitemap, the journey and all 11 low-fidelity screens as SVG, reruns its 11 checks (11 passed, 18 colour pairs among them), and fails if any file differs from the ones on this page. (evidence)
  • The site’s browser tests click through all 19 transitions of the clickable prototype in low and in high fidelity, including the dialog, Escape and the browser’s Back button, with axe checks for WCAG A and AA, and check that its high-fidelity colours are the token values.
  • On every pipeline, CI redraws the style guide, the component sheet (13 components) and 22 high-fidelity screens, and audits all 24 drawings: 24 passed; lowest text contrast 4.63:1, lowest control boundary 4.63:1. (evidence)
  • The site’s browser tests measure every line of text in the high-fidelity screens against the room it was laid out for, in the font the CI browser renders.

Not verified

  • Penpot cloud (penpot.app): the file was checked on a self-hosted instance only.
  • Editing by a person: the checks open and click the file; nobody has redesigned it in Penpot yet.
  • Export from Penpot to SVG, PDF or PNG.
  • Opening the SVG drawings in Penpot or Figma: both vendors document SVG as a way to move designs between tools, but nobody has tried it with these files.
  • A pixel comparison of the high-fidelity screens with Penpot or with the working page: unavailable, no such check exists yet.
  • Text width in the brand font, Source Sans Pro: the CI browser has no copy of it, so the text-fit check measures a substitute font.
  • Colour-vision simulation and a review by a designer: unavailable.
  • Writing to Penpot through a plugin or the MCP server. Browser tests do not prove native write access.
  • Figma: the file is Penpot-only and was not tried in Figma.
  • Use by real learners or by people who use assistive technology: no usability sessions have been run.

Professional review: Not required for this invented practice product, and none was done. The automated checks are not an accessibility audit, and nothing here is a conformance statement for a real product.
