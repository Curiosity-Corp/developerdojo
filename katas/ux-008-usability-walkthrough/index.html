Specialization kata · UX-008

Walk usability tasks and plan a session

Write the tasks a person would try, walk each one through the flow to find the shortest path and the errors on the way, then plan a moderated session to see what people really do.

The outcome

A task file for your flow, a walkthrough that shows the shortest path and the errors on the way for each task, and a session sheet ready for a moderated session.

For: Learners with a clickable prototype (UX-006) who have not run a usability session before.

Done when

  • Each task is a scenario with a goal, not an instruction that names a button
  • Each task has a start, a goal and a step budget, and the walkthrough passes or records each finding with a decision
  • Every error a user can hit on the way to a goal either leads to the goal or is a recorded finding
  • The session sheet asks for consent and records no name, email address or other personal data

You make: Usability walkthrough, Session plan. Outcome: Walk usability tasks.

Showcase and provenance

The Dojo’s worked example, made by the maintainers rather than by a learner: seven Pocket Invoice tasks walked through the flow, one finding, and a blank session sheet.

Why this stack

A walkthrough is cheap and repeatable, and it finds structural problems before anyone is asked to help. It cannot say what people do, so the kata ends with a plan for a session with a person, which the assistant cannot run for you.

Alternatives

  • Unmoderated remote testing service. Reaches more people faster, usually on a paid plan, and sends recordings of participants to a third party. Out of scope for this practice kata; not tried. Not tested for this recipe.
  • Heuristic review by an assistant. Fast, but it is the assistant’s opinion, not evidence of what people do. Use it only to suggest tasks to walk. Not tested for this recipe.

Agents and review gates

  1. Drafting assistant

    Rewrites each task as a scenario that names the goal and never the button, and suggests what to watch for.

    Review gate: You check every scenario against the flow and remove any that names a control before it goes into the task file.

  2. Reviewer

    Reads the walkthrough and the session sheet and checks that every finding has a decision and that the sheet collects no personal data.

    Depends on: Drafting assistant

    Review gate: A finding counts only when the reviewer names the task and the state.

Setup and smoke test

  1. Download the task file, the flow file and the pathway script from the UX pathway page into one folder, with the token file.
  2. Run the script with Node.js and open usability/walkthrough.md in the output folder.

Sign-in and access: None.

Prompts

Copy a prompt into the assistant you use. Replace anything that does not fit your situation, and never paste private or personal data you are not allowed to share.

Write task scenarios

Turns the jobs of your product into tasks a participant can try without being told which button to press.

You can also select and copy the text.

Practice exercise

Using moderated usability testing (GOV.UK Service Manual). From Using moderated usability testing (GOV.UK Service Manual).

Terms: Read on the publisher’s site. GOV.UK Service Manual guidance is published under the Open Government Licence v3.0 unless it says otherwise; the Dojo credits it and copies no text. Run sessions with people yourself. If a course or programme you take part in uses this guidance, follow its rules on AI assistance, and do not submit a session report an assistant wrote where those rules forbid it.

Execution and handoffs

  1. Drafting assistant: Write task scenarios with the prompt. Hand-off: You remove any scenario that names a control and write the task file.
  2. Learner: Run the script, read the walkthrough, and decide about each finding (fix the flow, or record it with a reason). Hand-off: The walkthrough and the session sheet go to the reviewer.
  3. Reviewer: Check each finding has a decision and the sheet collects no personal data. Hand-off: You run one moderated session with the sheet, with consent, and keep the filled-in copy private.

Failures and corrections

No failures have been recorded.

Adapt it

  • Fix the returning-user finding in the Pocket Invoice flow. Add a way from the sign-up error to sign in, rerun the script, and remove the accepted finding; the script fails until you do both.
  • Test with people who use a screen reader. Recruit through an accessibility organisation, allow more time per task, and test the built page, not the prototype.

Belt evidence

Belt stages are proposed practice stages, not issued credentials. Evidence below is what a reviewer would look for; it is not a record that anyone has shown it.

Evidence a reviewer looks for

  • For each task, the script finds the shortest path through the flow and checks its step budget, that every step is a button and that every error on the way leads to the goal; the browser tests replay each path in the prototype at three widths (Automated check)
  • One moderated session with a participant who has not seen the design, recorded on the session sheet with no personal data (Peer review)

Belt criteria

  • Practice: Reads the example walkthrough and explains the returning-user finding in their own words
  • Adapt: Fixes the returning-user finding in the flow (a way from the sign-up error to sign in), reruns the script and removes the accepted finding
  • Demonstrate: Writes tasks for the Randori flow, walks them, and runs one moderated session with the session sheet

Maintenance and caveats

Review cadence: Every six months, or when the GOV.UK guidance changes

  • This recipe is a draft: the example was built and checked by the Dojo maintainers, and no learner has run it yet.

  • The walkthrough checks what the flow allows, not what people notice or understand.
