Map the model to a sequence and an unpriced cost plan

Map the model's elements to construction tasks, derive each dependency from a relationship in the model or an open issue, and build an unpriced cost plan whose lines cite traced quantities.

The outcome

A preliminary model-to-sequence mapping and cost plan in which every link can be traced, and nothing is invented.

For: Learners who finished BIM-006 and BIM-007.

Done when

  • Every physical element is assigned to exactly one task, in the IFC file (IfcRelAssignsToProduct)
  • Each dependency cites the model relationship or the issue it comes from, and the order is computed; a cycle stops the script
  • The planned file is read back and matches what was written
  • Each cost line cites a traced quantity, a count of model elements or an open issue, and no rate is invented
  • The plan says it is preliminary practice, with no durations, rates or programme

You make: Schedule mapping, Quantity table. Outcome: Map model to schedule.

Showcase and provenance

The Dojo’s worked example, made by the maintainers rather than by a learner: the coordination model mapped to four construction tasks and an unpriced cost plan, each link traced to the model or the issue register, computed by the site’s CI on buildingSMART’s wall-with-opening-and-window sample.

Stack recipes

  • Ifcopenshell and python

Why this stack

A schedule or cost plan linked to a model is only useful if each link can be checked. Writing the tasks into the IFC file, rather than into a separate spreadsheet, keeps them in the open exchange format, and reading the file back shows what another IFC reader would find. Durations and rates are left out because no source for them has been chosen, and an invented number would look like evidence.

Alternatives

  • A scheduling tool linked to the model. Adds durations, calendars and a Gantt view. Each tool imports IFC tasks differently, and none was tested, so do not assume the tasks open the same way in one. Not tested for this recipe.
  • Unit rates from a published price book. Would price the plan, but most price books cannot be reused freely and their measurement rules differ. None was chosen. Not tested for this recipe.

Agents and review gates

  1. Coding agent

    Drafts the script that writes the tasks, assigns the elements and derives the dependencies.

    Review gate: Every dependency carries its reason; a dependency without one is rejected.

  2. Learner as reviewer

    Checks each dependency against the model relationships and the issue register, and checks each cost line against BIM-006.

    Depends on: Coding agent

    Review gate: Nothing is presented as a programme, an estimate or construction ready.

Setup and smoke test

  1. Create a virtual environment with Python 3.12: python3.12 -m venv .venv
  2. Install the pinned packages: .venv/bin/pip install --require-hashes -r /examples/bim-pathway/tools/requirements.txt
  3. Download the edited model and coordination-brief.json from /katas/bim-pathway into a new, empty folder. Work on copies.

Sign-in and access: None. Nothing here needs an account.

Execution and handoffs

  1. Coding agent: Writes the tasks and the dependencies into a copy and writes the cost plan. Hand-off: You check each reason and each cited quantity.
  2. Learner: Reads the plan against gates G4 and G5 of the review package.
  3. Learner: Writes what a planner and a quantity surveyor would add before anyone used it.

Failures and corrections

  • Observed: The work schedule's date changes on every run Correction: The add_work_schedule function in IfcOpenShell's sequence API stamps the current time. Set CreationDate and StartTime yourself if the file must be reproducible.
  • Observed: The order is right but nobody can say why Correction: Store the reason with each dependency when you create it. A typed order cannot be checked.

Adapt it

  • Resolve ISS-001 by rerouting the duct above the wall The duct no longer depends on the wall through the issue and the fire-stopping task has nothing to do; the plan changes because the evidence changed.

Belt evidence

Belt stages are proposed practice stages, not issued credentials. Evidence below is what a reviewer would look for; it is not a record that anyone has shown it.

Evidence a reviewer looks for

  • A planned IFC copy with a work schedule, four tasks, each element assigned to the task that builds it and three finish-to-start dependencies, read back from the written file and matching the Dojo's CI output (Automated check, against Industry Foundation Classes (IFC))
  • A cost plan in which each line cites a traced quantity, an element count or an open issue, and no line is priced (Automated check, against Industry Foundation Classes (IFC))
  • The learner names what a planner and a quantity surveyor would have to add before either is used (Self-check)

Belt criteria

  • Practice: Reproduces the task order T-010, T-020, T-030, T-040 and says which model relationship or issue gives each dependency
  • Adapt: Adds a task (for example, making good around the duct) with its own source for each dependency, and the order is still computed, not typed
  • Demonstrate: Explains to a partner why the plan has no durations or rates, and who would supply them

Maintenance and caveats

Review cadence: Every six months, when IfcOpenShell releases a new minor version, or when buildingSMART revises IFC

  • This recipe is a draft: the example was built and checked by the Dojo maintainers and CI, and no learner has run it yet.
  • The sample is a three-element test file plus one practice duct, not a building. Nothing learned from it is evidence about a real project.
  • No model, issue, sequence or quantity here is professionally reviewed or approved, and nothing is construction ready. The review package names the qualified reviewers and gates a real project would need.
  • This is a preliminary mapping, not a programme. There are no durations, calendars, resources or dates, because no source for them was chosen.
  • The cost plan is unpriced. It is not an estimate, a bill of quantities or an order, and the measurement rules a contract would set are not applied.
  • The planned IFC was read back with IfcOpenShell only. No scheduling tool was tested.
