Wire a clickable prototype with overlays and back paths

Turn the connected screens into a prototype a person can click through, with a dialog over the screen, every state change and a way back from each step.

The outcome

A clickable prototype of your flow in which every transition works, the dialog opens over the screen it belongs to, and every step has a way back.

For: Learners who have finished UX-002 and have connected low-fidelity screens.

Done when

  • Every transition in the sitemap can be clicked in the prototype
  • The dialog opens over the screen underneath and closes with its button and with Escape
  • Every screen has a way back, and the browser's Back button goes back one step
  • Focus moves to the new screen's heading, or into the dialog, after each step

You make: Prototype. Outcome: Wire clickable prototype.

Showcase and provenance

The Dojo’s worked example, made by the maintainers rather than by a learner: the Pocket Invoice clickable prototype in low and high fidelity.

Why this stack

Penpot prototypes run in View mode with overlays and back actions, and the Dojo's HTML prototype shows the same flow in a browser, so a learner can compare a design-tool prototype with a coded one. The assistant only drafts the interaction table; you wire and check it.

Alternatives

  • Figma. Widely used, with overlays and back actions in prototypes. The free Starter plan limits some features (for example 20 MCP tool calls a month); Professional seats cost $3 to $16 a month (figma.com/pricing, checked 2026-11-20). The example has not been tried in Figma. Not tested for this recipe.
  • Penpot MCP server with an agent. Lets an agent edit the open page directly, but uses a personal key with no permission scopes. Not run for this pathway: no native write by an agent was verified. Not tested for this recipe.

Agents and review gates

  1. Drafting assistant

    Turns your transition table into a list of interactions (trigger, destination, overlay or screen, way back).

    Review gate: You compare every interaction with the sitemap before it goes into the prototype.

  2. Reviewer

    Clicks through the prototype from the start and lists any transition that is missing, any overlay that does not close and any step with no way back.

    Depends on: Drafting assistant

    Review gate: A finding counts only when the reviewer can name the screen and the transition number it is about.

Setup and smoke test

  1. Open the Pocket Invoice clickable prototype in a browser.
  2. Open your connected low-fidelity screens from UX-002 next to it, in Penpot or as HTML.

Sign-in and access: None for the example. Your own Penpot account if you build in Penpot.

Smoke test

Do
In the example prototype, choose Create your first invoice, then Cancel, then press Escape.
Expect
The dialog opens over the new invoice form, and Escape closes it and returns to the form.
Result
Passed /examples/pocket-invoice-prototype/, walked by the site’s browser tests on every pipeline

Prompts

Copy a prompt into the assistant you use. Replace anything that does not fit your situation, and never paste private or personal data you are not allowed to share.

List the interactions

Turns the transition table into the interactions a prototype needs.

You can also select and copy the text.

Practice exercise

Prototyping (Penpot user guide). From Prototyping (Penpot).

Terms: Read on the publisher’s site under its terms. Credited, not copied. If a course or programme you take part in uses this exercise, follow its rules on AI assistance, and do not submit work an assistant wrote where those rules forbid it.

Execution and handoffs

  1. Learner: Click through the example prototype and note how each overlay opens and closes. Hand-off: Paste your transition table into the drafting assistant.
  2. Drafting assistant: List the interactions with the prompt. Hand-off: You check the list against the sitemap and wire the prototype.
  3. Learner: Wire every interaction in Penpot View mode or in HTML, with the dialog as an overlay. Hand-off: The prototype goes to the reviewer.
  4. Reviewer: Click through from the start, try Escape on every overlay and Back on every screen, and list gaps. Hand-off: You fix each gap and note what changed.

No failures have been recorded.

Adapt it

  • Add a confirm-send dialog before the invoice goes out. A new overlay with two ways out; the sitemap, the transition table and the prototype all change together.
  • The product must work on a phone held in one hand. Put the main action within thumb reach on every screen, and check that overlays still fit at 320 px.

Belt evidence

Belt stages are proposed practice stages, not issued credentials. Evidence below is what a reviewer would look for; it is not a record that anyone has shown it.

Evidence a reviewer looks for

  • A browser clicks every transition of the prototype, opens and closes the dialog with a button and with Escape, uses the browser's Back button, and runs axe for WCAG A and AA, in low and high fidelity (Automated check)
  • A partner who has not seen the flow completes the happy path and one error path without help (Peer review)

Belt criteria

  • Practice: Clicks through every transition of the example prototype, including the dialog, Escape and Back
  • Adapt: Adds an overlay of their own (for example a confirm-send dialog) with a way to close it and a way on
  • Demonstrate: Wires the Randori flow as a prototype in which every state is reachable and every overlay closes
