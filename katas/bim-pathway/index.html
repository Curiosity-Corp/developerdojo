Architecture and BIM · Pathway

From an IFC file to checked information.

Ten katas on one small, openly licensed building model. Each step has a real file you can open and a check result that CI computes on every pipeline.

Start with BIM-001Download the model

01 / The files

One wall, one opening, one window

The model is buildingSMART’s wall-with-opening-and-window test file: schema IFC4, lengths in millimetre. It is tiny on purpose, so every entity can be read and every check can be followed by hand. It is a test file, not a building.

  • The original model (IFC, CC BY 4.0, buildingSMART International), unchanged.
  • The practice requirements (IDS 1.0 XML): six requirements written for this pathway.
  • The edited copy (IFC, CC BY 4.0 adaptation): the BIM-004 change, rebuilt byte for byte by CI.
  • The check summary (Markdown) and every result as JSON under the manifest, with tool versions and file hashes.
  • The pathway script (Python, MIT) and its pinned packages, so you can rerun every check yourself.
  • README: licences, how to rerun the checks, and what they do not cover.

Mesh is not BIM. The 3D room scan is a surface you can look at; this model is data with types, properties and relationships you can query and check.

03 / The steps

Ten katas, in order

Each kata has a brief, prompts, checks and the evidence for the checks the Dojo has run. They are drafts: the Dojo built the example and CI checks it, and no learner has run them yet. Do the foundations first: Compare AI instructions and Spot a context trap. If you have not read an IFC file before, Find the story in a building model walks through the same sample by hand.

  1. BIM-001 Inspect an IFC model

    Schema, units, the spatial tree, every element and how the opening and window relate to the wall.

  2. BIM-002 Read the property sets

    Every property on the wall and window, with its type, and the ones that are empty.

  3. BIM-003 Check the model against IDS requirements

    Run six practice requirements with IfcTester and explain the one that fails.

  4. BIM-004 Change the model and check it again

    One scoped edit, every GlobalId kept, then IDS, schema and geometry checks rerun on the copy.

  5. BIM-005 Build a 3D mesh and check its shape

    Tessellate the wall and window to an OBJ and check each mesh from its triangles alone: closed, oriented, holes, area and volume.

  6. BIM-006 Trace quantities to the model objects

    Eleven quantities, each with its source entities, unit, method and assumption, cross-checked against the built geometry.

  7. BIM-007 Find a clash and raise it as a BCF issue

    Add a practice duct, find where it clashes by two routes, and write an issue register as BCF that validates and reads back.

  8. BIM-008 Map the model to a sequence and an unpriced cost plan

    Assign each element to the task that builds it, derive each dependency from the model or an issue, and cite a traced quantity on every cost line.

  9. BIM-R01 BIM Randori: an unseen requirement change

    A partner reveals one new requirement after you start; meet it without breaking the others.

  10. BIM-R02 Specialist BIM Randori: a changed requirement, format or tool

    A specialist changes a clearance rule, the exchange format or the clash tool after you start; show what changes for the reviewers.

06 / Coordination, sequence and review

A clash, an issue, a sequence and who must review it

Construction work is a third layer, kept apart from the shape and the building information. BIM-007 adds one practice duct to the edited copy, routed through the wall on purpose; BIM-008 maps the result to tasks and an unpriced cost plan. CI recomputes all of it on every pipeline.

Clashes, by two routes (BIM-007)

The practice duct against each physical element, in metres
PairBox route overlap m³Box route gap mIfcOpenShell clash tree (collision mode)
duct and #45=IfcWall0.030hard clash, faces cross
duct and #102=IfcWindow00.03no hard clash

The two routes agree; the script writes nothing if they do not. Validation exception: IfcClash 0.9 intersection mode (tolerance 0.002 m) reports no clash here, although its collision mode and the box route both find ['#45=IfcWall']. It is recorded and not relied on. Do not read an empty result from one mode as no clash. Box arithmetic is right here only because every element is box-shaped, which the script checks. The coordination model has 0 schema issues. Coordination model (IFC) · clash results (JSON).

Issue register

  • ISS-001 Clash, open: D-01 Supply duct (practice) passes through Wall for Test Example with no opening for it. Review gates G2, G3.

The register is written as BCF 3.0, with CSV and JSON copies. Every XML part is valid against buildingSMART’s official BCF-XML schema files, kept unchanged (7 of 7 proven by their git blob ids; see the check), and bcf-client reads it back with 1 topic selecting 2 elements that are in the model. No other BCF tool has opened it, so do not assume one will show it the same way.

Specialist Randori cards (BIM-R02)

  • CARD-R changes the requirement: Keep 0.05 m clear between the duct and every other element, not only avoid touching. Result: 1 new issue(s): ISS-002.
  • CARD-F changes the format: The receiving tool reads BCF 2.1 only. Export the same issues as BCF 2.1 and say what does not carry over. Result: valid against buildingSMART's official BCF 2.1 schema files and read back (1 topic(s)); some information does not carry over.

08 / What is checked

Verified, and not verified

Verified

  • The model is the pinned buildingSMART file, unchanged (SHA-256 73b0e45d931d…, checked by the site’s tests).
  • Both IDS files open with XML schema validation on, as IDS 1.0.
  • On every pipeline, CI installs the pinned packages by hash, reruns the inspection, property, IDS, schema and geometry checks on the original and the edited copy and the Randori cards, rebuilds the edited file, and fails if any output differs from the files on this page. (evidence)
  • The edit changes one property and keeps every GlobalId. (evidence)
  • The 2 meshes in the OBJ are closed and consistently oriented, and each enclosed volume equals the volume IfcOpenShell reports, computed from the triangles alone. (evidence)
  • A practice duct added to the edited copy clashes with the wall; IfcOpenShell’s clash tree and box arithmetic on the built shapes agree on every pair, and the script writes nothing if they do not. (evidence)
  • The issue register is written as BCF 3.0; every XML part is valid against buildingSMART’s official BCF-XML schema files, kept unchanged and proven by git blob id, and bcf-client reads the file back with every selected GlobalId found in the model. (evidence)
  • The planned IFC copy holds four tasks, each element assigned to the task that builds it, and finish-to-start dependencies each derived from a model relationship or an open issue; it is read back and matches what was written. (evidence)
  • Every cost line cites a traced quantity, an element count or an open issue; no line is priced. (evidence)
  • Each of the 11 quantities names its source entities, GlobalIds, unit, method and assumption; 4 cross-checks between the IFC parameters and the built geometry agree, and the script writes nothing if one does not. (evidence)

Not verified

  • Any real building, design value or project requirement. The requirements are invented for practice, and the sample is a test file.
  • EXPRESS where-rules and buildingSMART’s own validation service: the schema check ran with EXPRESS rules off.
  • Coordination on a real, federated multi-discipline model: the only clash is with one practice duct added on purpose, and the box route holds only because every element is box-shaped.
  • That any tool other than bcf-client reads the BCF files the same way: no BCF viewer or coordination tool was tested.
  • Cost, procurement or construction quantities: the cost plan is unpriced, no unit rates are applied and no measurement rules of a contract are followed.
  • A construction programme: the sequence has no durations, calendars or resources, and no scheduling tool was tested.
  • Any review gate in the review package: none has been reviewed, and nothing is construction ready.
  • Tolerances, structural behaviour or constructability of any shape.
  • Viewing the OBJ in a 3D viewer: the mesh was checked from its triangles, not looked at.
  • Opening the files in a BIM authoring tool or a web IFC viewer, and round trips through other tools.
  • Use by real learners: no learner has run these katas yet.

Professional review: None. Nothing here has professional, regulatory or construction approval of any kind, and a real project needs the qualified reviewers its contract and jurisdiction name.

The field template

What this field adds to the shared foundations

Every sector pathway follows the same template: the field's own terms and procedures, the standards its work is read against, the files it produces, belt criteria, and the qualified review a real use needs. The katas build on the shared foundations and do not repeat them.

Terms of the field

IFC entity
A typed object in an Industry Foundation Classes model, such as a wall, a window or a storey, with a stable GlobalId.
Spatial structure
The tree that places every element in a site, building and storey.
Property set
A named group of properties attached to an element, such as fire rating or whether a wall is external.
Information requirement
What a model must contain for a given use; IDS writes it in a form software can check.
Quantity take-off
Lengths, areas, volumes and counts read from the model and traced to the elements they come from.
Coordination issue
A problem found between disciplines, recorded with its viewpoint and elements; BCF is the open exchange format.

Procedures practised

  1. Inspect a model: schema, units, spatial tree and relationships (BIM-001)
  2. Check the model against its information requirements, change it and check again (BIM-002, BIM-003, BIM-004)
  3. Derive geometry and quantities and trace each one to its elements (BIM-005, BIM-006)
  4. Raise coordination issues between disciplines (BIM-007)
  5. Map the model to a construction sequence and an unpriced cost plan (BIM-008)

Standards cited, by version

  • Industry Foundation Classes (IFC), IFC4 ADD2 TC1 (ISO 16739-1:2018), as declared by the sample file (read against in BIM-001, BIM-002, BIM-003, BIM-004, BIM-005, BIM-006, BIM-007, BIM-008, BIM-R01, BIM-R02)
  • Information Delivery Specification (IDS), 1.0 (read against in BIM-003, BIM-004, BIM-R01)
  • BIM Collaboration Format (BCF), BCF-XML 3.0 (the register); BCF-XML 2.1 (the Randori format card) (read against in BIM-007, BIM-R02)

Citing a standard says which edition the work is read against. It never says the work meets it.

Native files the katas produce

model evidence, property table, ids report, edited model, mesh file, quantity table, issue register, schedule mapping.

Belt criteria

10 of 10 katas have a practice criterion; 10 of 10 katas have a adapt criterion; 10 of 10 katas have a demonstrate criterion. Each recipe page lists them. Belts are proposed practice stages, not credentials.

09 / Staged

Proposed, not built yet

These parts of a built-environment pathway are proposed. Nothing below has been run, and no result is shown for any of them.

  • Federated, multi-discipline coordination Proposed
    The coordination kata clashes one practice duct against one wall. Coordinating real architectural, structural and services models needs a set of openly licensed models that may be reused; none has been chosen.
  • Priced cost and a timed programme Proposed
    The cost plan is unpriced and the sequence has no durations. Rates and productivity need sources that may be reused and the measurement rules a contract sets; none has been chosen.
  • Other BCF and scheduling tools Proposed
    Only bcf-client and IfcOpenShell have read the files back. No BCF viewer, coordination tool or scheduling tool has opened them.
  • Full schema rules and outside validation Proposed
    EXPRESS where-rules and buildingSMART’s validation service have not been run.
  • Authoring tools and viewers Proposed
    No round trip through a BIM authoring tool, and no viewer has opened the OBJ.
  • Civil works and digital twins Proposed
    Out of scope for a single-wall sample.
  • Professional review Proposed
    Every gate in the review package is not reviewed. A real review needs the qualified people the package names.

No model, mesh, quantity, issue, sequence or check on this page is professionally reviewed or approved, and none is fit for construction. A real project needs the qualified reviewers its contract and jurisdiction name, for example an architect, an engineer, a quantity surveyor or a BIM manager, and their approval before anyone builds, prices or orders from it.
