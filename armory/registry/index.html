Claude Code

Anthropic

A coding agent that reads and edits files and runs commands in a terminal, with permission prompts and a non-interactive print mode.

Checked 20 November 2026 · version 2.1.329 tested; 2.1.330 published on 2026-11-20 and not tested. Review due: check the source before relying on this entry.

Review due.Last verified 20 November 2026 by the catalog maintainer.

A change was reported on 2026-11-22: Claude Code 2.1.330 is now the current release. The smoke test and the recorded runs used 2.1.329, so steps and permissions have not been checked on the version you will install. Treat versions, prices, steps and permissions here as possibly out of date. Check the linked source before you rely on it, and practise with test data.

Versions, permissions and evidence
Version
2.1.329 tested; 2.1.330 published on 2026-11-20 and not tested. Tested version from the FND-001 run files; latest from the npm registry (npm view @anthropic-ai/claude-code).

Proprietary. The package says "SEE LICENSE IN README.md"; Anthropic's commercial or consumer terms apply.

macOS, Linux and Windows, per the setup guide. Tested on Linux only.

Permissions

Reads
Reads files in the working folder without asking; other read-only tools follow the permission settings.
Writes
Asks before editing files unless a permission mode or allow rule says otherwise.
Runs code
Asks before running shell commands unless allowed by a rule.
Network
Sends prompts and file content it reads to the model provider. Web fetch and MCP servers add more network access when enabled.
Least access
Use print mode with tools disabled (--tools "") and no inherited settings, as FND-001 does, or the default ask-before-acting mode in a disposable folder.

What it does

  • generate: Answers a prompt in print mode and returns JSON with the result, time and list-price cost. Tested
  • read: Reads and searches files in the working folder. Documented, not tested
  • edit: Creates and edits files after approval. Documented, not tested
  • execute: Runs shell commands after approval. Documented, not tested

Setup

  1. Install it from the official setup guide and sign in.
  2. Check your plan and the cost guidance before running anything long.
  3. For a reproducible run, use print mode with no tools and no inherited settings in an empty folder.

MCP server · reference implementation

MCP filesystem server

Model Context Protocol project

The reference MCP server for file operations, limited to the directories you pass when you start it.

Checked 20 November 2026 · version 2.4.0. Review due: check the source before relying on this entry.

Verified.Last verified 20 November 2026 by the catalog maintainer. Next check by 18 February 2027.

Versions, permissions and evidence
Version
2.4.0. npm view @modelcontextprotocol/server-filesystem; the same version reported itself at start-up.
Licence
In transition from MIT to Apache-2.0: new contributions are Apache-2.0; older ones stay MIT until relicensed (repository LICENSE). The npm package itself ships no licence file.
Platforms
Anywhere Node.js runs. Tested on Linux with Node.js 24.
Cost and plan
Free. No account or service.
Sign-in
None. Access is limited by the directories passed on the command line (or MCP roots from the client).

Supported combinations

  • Minimal MCP stdio client (protocol 2025-06-18) on Linux, Node.js 24 Tested
  • Any MCP client that starts stdio servers on macOS, Linux, Windows Documented, not tested

Permissions

Reads
Reads, lists and searches files under the allowed directories.
Writes
Creates, overwrites, edits, moves and copies files under the allowed directories. write_file, edit_file and move_file are marked destructive.
Runs code
Runs no commands. It is itself a Node.js program started with npx.
Network
None for its tools. npx downloads the package from the npm registry on first start.
Least access
Allow one disposable folder. If the task only reads, give the agent only the read tools (most clients can disable tools).

What it does

  • read: list_directory and read_text_file returned the sandbox listing and file content. Tested
  • create: write_file created created.txt in the sandbox. Tested
  • edit: edit_file changed one line and returned a diff. Tested
  • read: Reading /etc/hostname, outside the sandbox, was refused with "Access denied". Tested
  • delete: No delete tool; move_file and write_file can still replace or move content. Documented, not tested

Setup

  1. Create an empty folder for the agent to use.
  2. Add the server to your MCP client: npx -y @modelcontextprotocol/server-filesystem@2.4.0 <folder>. Pin the version.
  3. List its tools in the client and disable the write tools if the task does not need them.

Smoke test, 20 November 2026: passed

Setup
Linux, Node.js 24.22.3, clean environment, one disposable allowed folder.
Action
List tools, then list, read, create and edit inside the sandbox, then read a file outside it.
Expected
Inside the sandbox every call succeeds; the outside read is refused.
Observed
16 tools listed. All four sandbox calls succeeded and the file contents matched afterwards; the outside read returned "Access denied - path outside allowed directories".

Evidence: mcp-filesystem.json

Provenance review, 20 November 2026

Publisher, npm metadata, provenance attestation and repository licence; tool annotations from tools/list.

  • npm 2.4.0 carries an SLSA provenance attestation linking it to the modelcontextprotocol/servers repository.
  • Write tools are annotated destructive; an agent with them can overwrite any file in the allowed folders.
  • The allowed-folder check held in the smoke test for a plain path outside the folder.

Not checked: No source audit; symlink and path-traversal cases were not tested.

Limitations

  • One platform tested. Symlinks, Windows paths and client-supplied roots were not tested.
  • An agent with write tools can destroy work inside the allowed folder; keep backups or use a copy.

Version
0.0.86. npm view @playwright/mcp and the GitHub release; the server reported Playwright 1.66.0-alpha-2026-11-18.
Licence
Apache-2.0 (npm and repository). Sites you visit have their own terms.
Platforms
Anywhere Node.js and a Playwright browser run. Tested on Linux with headless Chromium.
Cost and plan
Free. No account.
Sign-in
None for the server. With a persistent profile, the browser keeps any sign-ins, so use --isolated or a test profile.

Supported combinations

  • Minimal MCP stdio client (protocol 2025-06-18) on Linux, Node.js 24, headless Chromium Tested
  • Any MCP client that starts stdio servers on macOS, Linux, Windows; Chrome, Firefox, WebKit or Edge Documented, not tested

Permissions

Reads
Reads page content and accessibility snapshots, console messages and network requests of the pages it opens.
Writes
Acts on pages: clicks, types, fills forms, uploads files. Writes snapshot files into a .playwright-mcp folder in its working directory.
Runs code
browser_evaluate and browser_run_code_unsafe run JavaScript in the page or against the Playwright API.
Network
The browser can reach any site unless you restrict it. The README says origin lists are not a security boundary.
Least access
Run --headless --isolated in a disposable working folder, with only a test site and no signed-in profile.

What it does

  • navigate: browser_navigate opened an inline test page. Tested
  • edit: browser_click toggled a button; the page state changed. Tested
  • read: browser_snapshot reported the button as "Planted" and pressed. Tested
  • create: Snapshot files were written to .playwright-mcp in the working folder. Tested
  • execute: Runs page JavaScript and Playwright code through browser_evaluate and browser_run_code_unsafe. Documented, not tested

Setup

  1. Install a Playwright browser, or let the server tell you which one it needs.
  2. Add it to your MCP client: npx -y @playwright/mcp@0.0.86 --headless --isolated. Pin the version.
  3. Start it in an empty working folder, because it writes snapshot files there.

Penpot (Kaleidos)

An open-source design and prototyping tool that runs in the browser, on penpot.app or on your own server. Its files hold boards, components, design tokens and clickable prototype flows, and export as an open .penpot file.

Checked 28 November 2026 · version 2.19.5 (released 2026-11-24), tested self-hosted; @penpot/library 1.3.0 writes the file. Review due: check the source before relying on this entry.

Verified.Last verified 28 November 2026 by the catalog maintainer. Next check by 26 February 2027.

Versions, permissions and evidence
Version
2.19.5 (released 2026-11-24), tested self-hosted; @penpot/library 1.3.0 writes the file. GitHub releases API (latest release) and the running instance's version.txt; npm registry for the library.
Licence
MPL-2.0 for Penpot (the repository LICENSE file, as GitHub reports it) and for @penpot/library (npm licence field). penpot.app accounts also accept Penpot's terms of service.
Platforms
Any current desktop browser, on penpot.app or a self-hosted instance (Docker Compose, Kubernetes and other paths in the self-hosting guide). Tested: self-hosted 2.19.5 container images on Linux, driven by Chromium.
Cost and plan
Self-hosted: free. penpot.app, as listed on its pricing page: Professional $0 (up to 8 team members and unlimited viewers, 10 GB storage, 7 days of autosaved versions and file recovery); Unlimited $7 per editor a month, capped at $175 a month (25 GB, 30 days); Enterprise $25 per member a month (unlimited storage, 90 days, SSO); a private server from $50,000 a year. Unlimited and Enterprise have a 14-day trial. The page lists no plan limit on the MCP server or plugins.
Sign-in
A Penpot account: on penpot.app, or on your own instance, where the administrator decides whether people can register. The MCP server needs a personal MCP key from your account.

Supported combinations

  • Self-hosted Penpot 2.19.5 in Chromium (Playwright), the file written by @penpot/library 1.3.0 on Linux Tested
  • penpot.app (Penpot cloud) on Any current desktop browser Documented, not tested
  • Self-hosted Penpot 2.19.5 in Chromium (Playwright), a plugin installed from its manifest URL with content:write on Linux Tested
  • Penpot MCP server with an MCP-capable agent, through the plugin in an open Penpot tab on Any current desktop browser Documented, not tested

Permissions

Reads
Reads the files of the teams your account belongs to. Viewers on a shared link see the file in View mode only.
Writes
Editors change files in the workspace; import creates a new file in a project you choose. The MCP server can create, rename, move, delete and restyle shapes on the page open in your browser, and its key has no permission scopes. Plugins ask for permissions such as content:write when you install them; Penpot asks again when an update needs more, and its dialog shows only the widest line (content:read with content:write reads "Read and modify the content of files that users have access to").
Runs code
Runs in the browser tab. A self-hosted instance also runs the backend, frontend and database containers you start; plugins run their own code in your tab.
Network
Sends your files to the Penpot server you use (penpot.app or yours). A default self-hosted frontend fetches Google Fonts and dashboard templates from the internet unless the air-gapped configuration is on.
Least access
Practise in a file and a team you can lose. Import a copy of a .penpot file rather than the only one, leave the MCP server off unless you are trying it on a practice file, and on your own instance keep registration closed after you create your account.

What it does

  • create: Imported the Pocket Invoice .penpot file through the import-binfile API as a new file: five pages, 11 state boards on each prototype page, 8 main components, 16 library colours, 5 type styles and both token sets with the Light theme. Tested
  • navigate: Clicked through both prototypes in View mode: 22 clicks per flow reached every one of the 19 transitions, including the dialog overlay, its close action and every back path. Tested
  • edit: Opened every page in the workspace, where Penpot laid out the generated text and saved it to the file (at least 95% of text layers on each page). Tested
  • read: Exported the imported file again as .penpot (export-binfile) and imported that copy: same pages, boards, interactions, components and token sets. Tested
  • generate: Exports boards and layers as PNG, JPEG, WEBP, SVG or PDF, and all boards of a page as one PDF (needs the exporter service on a self-hosted instance). Documented, not tested
  • edit: A plugin installed from its manifest URL, with content:write allowed in Penpot's dialog, added a board, a rectangle and a text to the open page through the Plugin API; a new session read them back from the server and found them in the exported .penpot, with the rest of the file kept (checked 2026-11-28). Tested
  • edit: An AI agent can change the open page through the MCP server, which acts through a plugin in your open tab. Documented, not tested

Setup

  1. Create a penpot.app account (the Professional plan is $0), or run your own instance with the self-hosting guide.
  2. In Projects, choose Import, pick the .penpot file and confirm.
  3. Open every page of an imported file once in the workspace before you use View mode, so Penpot lays out its text.
  4. Press Play on a page with a flow to try the prototype.

Provenance review, 28 November 2026

Publisher of the container images and the npm library, registry signatures, licence, and the MCP and plugin permission model in the documentation.

  • The container images are published by the penpotapp organisation on Docker Hub; the tested digests are recorded in the evidence file.
  • @penpot/library 1.3.0 carries npm registry signatures but no npm provenance (SLSA) attestation.
  • The MCP key gives an agent write access to the open page, and its documentation names no permission scopes. A plugin's permissions are granted when it is installed and asked for again only when an update needs more; content:write lets it change any file you can open while it runs.
  • Penpot 2.19.5 ships its content security policy in report-only mode. With it enforced, a plugin's own window from another origin is blocked unless that origin is added (PENPOT_CSP_FRAME_SRC_EXTRA); the plugin check logged the report-only warning.
  • Since 2.19 a default self-hosted backend starts with its admin console flag on; leave it on and configure it, or switch it off, before opening registration.

Not checked: No source audit, no image vulnerability scan, no test of the MCP server, and no plugin permission other than content:read and content:write.

Limitations

  • Only a self-hosted 2.19.5 instance was used. penpot.app, the MCP server, plugins from the public list and exports to SVG, PDF or images were not run; one plugin of our own was, with content:write only.
  • The smoke test imports, lays out, clicks and exports a generated file. No person has edited it in Penpot.
  • Plan prices and limits are read from the pricing page on the check date; Penpot can change them.

Stack recipes

A recipe names the tools a kata expects. Where you choose the tool yourself, the recipe says so instead of naming a product.

An assistant and a browser

The starting stack for most katas: any AI assistant you can use, and a browser to open and check what it made.

  • Your choice: An AI assistant you can access, in a chat app, browser or CLI. Drafts and explains
  • Your choice: A current web browser. Opens the result so you can check it yourself

Used in 8 katas: Change the instructions, Can a document steer your agent?, Design a user journey, Inspect an IFC model, Compare lighting energy, Open-source patch lab, Rescue messy data, Explore a 3D room

Git and Node.js

A local project stack: Git records every change, Node.js runs the project's scripts and checks.

  • Git: Records, compares and restores changes
  • Your choice: Node.js, a current LTS release. Runs the project's scripts and checks

Used in 1 kata: Open-source patch lab

Penpot and a browser

The UX pathway stack: Penpot, an open-source design tool that runs in the browser (penpot.app or self-hosted), and a browser to try the prototype and the built page.

  • Penpot: Holds the editable sitemap, wireframes, tokens, components, the one-canvas journey and the clickable prototype (penpot.app, where the Professional plan is $0, or your own instance)
  • Your choice: A current web browser. Runs Penpot and opens the built page so you can check it yourself

No published kata uses it yet.

IfcOpenShell, IfcTester and Python

The BIM pathway stack: open-source Python libraries that read, edit and check IFC models against IDS requirements, run on your own machine or in CI.

  • IfcOpenShell: Reads and edits the IFC model, validates it against the schema and builds its geometry
  • IfcTester: Checks the model against the requirements in an IDS file
  • Your choice: Python 3.12 in a virtual environment. Runs the pinned libraries and the pathway script
  • Your choice: A text editor that shows XML. Reads and edits the IDS file

No published kata uses it yet.

Python and its standard library

The stack of the agriculture, science, finance, manufacturing, media, education, health and robotics pathways: one Python script that needs no packages, so it runs offline on any machine with Python 3.12 or later, and a spreadsheet to look at the CSV results.

  • Your choice: Python 3.12 or later, with no extra packages. Runs the pathway script: reads the input record, reproduces the published worked examples and computes every result
  • Your choice: Any spreadsheet app or a text editor. Opens the input record and the CSV and JSON results so you can check a row yourself

No published kata uses it yet.

Claude Code in print mode, with no tools

The FND-001 comparison stack: one non-interactive Claude Code call per run, with every tool turned off, so the only thing the agent can do is answer; a separate browser check scores what it wrote.

  • Claude Code: Runs the brief once in print mode, with no tools, and saves the answer
  • Claude Sonnet 5.5: Writes the page from the brief
  • Your choice: Playwright with axe-core, or any browser check you can repeat. Opens each saved page and runs the same checks on every run

No published kata uses it yet.

Choose a stack for your task

  1. Name the outcome and choose an assistant or harness you can access.
  2. List the data, files and actions the task actually needs. A skill is instructions; an MCP server or CLI may provide actions.
  3. Inspect the source, version, licence, permissions and compatibility. Start with fictional data and the smallest useful access.
  4. Check the output and record what you tested. A successful installation or a model’s assurance does not prove the result is correct.
